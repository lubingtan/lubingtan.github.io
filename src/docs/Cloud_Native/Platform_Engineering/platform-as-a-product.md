# 平台工程：把工程能力变成可复用的产品

> 平台不是“更大的运维团队”，也不是“一个门户”。平台是**一组按用户需求定义、以一致体验交付的能力集合**。平台团队对接口与体验负责，不必对所有实现负责。

## 1. 先划清边界

| 是平台 | 不是平台 |
|---|---|
| 把高频、通用、非差异化的工程能力沉淀为自助服务 | 把所有基础设施都收归一个团队审批 |
| 用黄金路径降低认知负荷，同时保留逃生通道 | 用强制手段统一工具链 |
| 对开发者、测试、SRE、数据/算法以及 agent 提供一致接口 | 只服务人类开发者的 Web 门户 |
| 像产品一样有用户、路线图、SLA、成本和弃用策略 | 一堆脚本、Wiki 和“找某某同学开权限”的集合 |
| 默认安全、默认可观测、默认可回收 | 事后补安全扫描与审计 |

CNCF 的定义是：平台是“按用户需求定义和呈现的集成能力集合”，它桥接能力提供者与平台用户，并在过程中实施安全、性能、成本和一致性方面的策略。平台团队最重要的产出不是机器，而是**接口（GUI/CLI/API/文档/模板）与体验**。

**Thinnest Viable Platform（TVP）** 是这里的关键约束：平台应薄到只封装“企业特有但团队通用”的部分，其余尽量复用托管服务或基础设施团队的能力。平台越大，维护成本、认知负荷和过时风险越高。

## 2. 能力地图

### 2.1 通用工程能力

| 域 | 能力 | 典型实现 | 平台化后的形态 |
|---|---|---|---|
| 入口与体验 | 服务目录、脚手架、文档、CLI | Backstage、Port、自定义门户 | 自助创建、可发现、可搜索 |
| 构建与测试 | 编译、单测、集成、扫描 | Actions、Tekton、Jenkins、Buildpacks | 可复用流水线模板、远程缓存 |
| 交付与验证 | GitOps、渐进发布、回滚 | Argo CD/Flux、Argo Rollouts、Flagger | 一键发布、自动分析、自动回滚 |
| 制品 | 镜像/包仓库、签名、SBOM | Harbor、OCI Registry、Cosign | 不可变制品、准入校验 |
| 环境 | 开发/测试/预览/生产环境 | Crossplane、vCluster、Terraform、Cluster API | 环境即服务、TTL、配额 |
| 数据 | 数据库、缓存、对象存储、消息 | 托管服务、Operator | 按需申请、备份/恢复、数据分级 |
| 身份与密钥 | 服务身份、密钥、证书 | SPIFFE/SPIRE、External Secrets、cert-manager | 短时凭证、自动轮转 |
| 安全与策略 | 扫描、策略、运行时防护 | OPA/Kyverno、Trivy、Falco | 默认策略、例外可审计 |
| 可观测 | 指标、日志、Trace、Profile | OpenTelemetry、Prometheus、Grafana | 开箱即用、SLO 模板 |
| 成本 | 配额、计量、分摊 | OpenCost、Kubecost、云账单 | showback/chargeback |

### 2.2 AI 应用特有的能力

AI 应用不是“多了一个模型调用”，它引入了一组新的工程对象：prompt、模型版本、评测集、检索索引、工具、guardrail、token 成本。平台需要把这些对象纳入统一治理。

| 能力 | 解决的问题 | 平台化要点 |
|---|---|---|
| 模型网关 | 多模型接入、路由、降级、限流 | 统一 API、配额、缓存、可观测、成本归集 |
| Prompt 注册与版本 | prompt 漂移、回滚、审计 | 像代码一样版本化、Code Review、灰度 |
| 评测服务 | 质量回归、模型切换决策 | 数据集版本、judge 校准、报告归档、CI 集成 |
| RAG/数据管道 | 知识更新、权限过滤、召回质量 | 数据分级、索引版本、引用溯源 |
| Agent 运行时 | 工具调用、沙箱、长任务 | 隔离、超时、预算、人工审批、审计 |
| 工具/MCP 注册 | 工具发现、权限、供应链 | 签名、allowlist、scope、版本 |
| Guardrail | 内容安全、PII、越权 | 策略即代码、命中记录、可解释 |
| 算力 | GPU 共享、队列、配额 | 与 [Kueue](../Kubernetes/Scheduling/kueue.md)、[HAMi](../AI_Infrastructure/Accelerators/hami.md) 集成 |

AI 能力的平台化有一个常见误区：为每个团队单独搭一套“模型调用服务”。更合理的做法是提供**共享的模型网关 + 评测基线 + 成本看板**，把差异化留给应用层。

## 3. 八条设计原则

1. **平台即产品（Platform as a Product）**：有明确的用户画像、Jobs-to-be-Done、路线图、采用漏斗和弃用策略；用“用户是否愿意持续使用”而不是“功能是否上线”衡量成功。
2. **黄金路径，不是黄金牢笼（Golden Path, not Golden Cage）**：默认路径要好走、有主见，但必须可选、可组合、有逃生通道；平台不阻止团队使用平台外的能力。
3. **API 优先、声明式优先**：每项能力先有 API/CRD/CLI，再有 UI；期望状态可版本化、可 reconcile，而不是一次性脚本。
4. **自助服务 + 内生护栏**：用户无需工单即可获得能力；安全、配额、合规通过策略自动执行，而不是靠人工审批。
5. **降低认知负荷**：提供合理默认值、隐藏实现细节，但保留可观测性与可配置性；“简单默认 + 可深入”优于“全部暴露”。
6. **可组合、可替换**：能力之间通过标准接口组合；底层供应商可替换，用户体验保持一致。
7. **默认安全、默认合规**：最省事的路径就是最安全的路径；例外必须显式、可审计、有期限。
8. **用结果度量**：采用率、首次成功时间、交付指标、单位成本；不用“能力数量”“页面访问量”自嗨。

## 4. 能力服务化的四级阶梯

复用不是“把代码抽成库”这么简单。共享库会制造版本耦合，服务化则要求契约与兼容性。可以把复用成熟度分为四级：

| 级别 | 复用单位 | 接口 | 治理 | 适用场景 |
|---|---|---|---|---|
| L1 | 脚本/代码片段 | 复制粘贴 | 无 | 一次性任务 |
| L2 | 可复用流水线/模板/Action | 参数化模板 | 版本 + CI 测试 | 构建、扫描、部署等标准步骤 |
| L3 | 共享服务/API/CRD | OpenAPI/CRD/CLI | 配额、SLO、审计 | 环境、数据库、模型网关 |
| L4 | 自助产品 | 门户 + API + MCP | 计量、计费、生命周期 | 多团队规模化使用 |

大多数平台停留在 L2：模板很多，但仍需人执行。L3 的关键是**把能力变成有契约的服务**；L4 的关键是**把服务变成有生命周期的产品**（申请、配额、升级、弃用、计费）。

### 4.1 能力契约

每项平台能力都应有一份“契约”，至少包含：

| 字段 | 说明 |
|---|---|
| 名称/版本/Owner | 唯一标识、语义化版本、负责团队 |
| 用户与场景 | 谁用、解决什么问题、不解决什么问题 |
| 接口 | API/CLI/UI/MCP，以及认证方式 |
| 输入/输出 Schema | 机器可校验，错误码稳定 |
| 配额与限流 | 默认值、上限、申请方式 |
| SLO/RTO/RPO | 可用性、延迟、恢复目标 |
| 安全与合规 | 数据分级、权限模型、审计事件 |
| 幂等与重试 | 哪些操作可重试、幂等键 |
| 依赖与弃用 | 依赖的服务、弃用时间表 |
| 文档与支持 | 示例、FAQ、on-call 联系方式 |

契约的价值在于：人类能读，agent 也能读；测试能断言，审计能追溯。

### 4.2 黄金路径的解剖

一条真正可用的黄金路径，不是“文档 + 模板”，而是一条**第一天就能跑通的走查骨架（walking skeleton）**：

1. **仓库脚手架**：目录结构、依赖、lint、测试、CODEOWNERS、AGENTS.md；
2. **流水线**：构建、单测、扫描、制品签名、部署到 dev；
3. **环境**：dev/staging/prod 的申请与回收；预览环境按 PR 创建；
4. **可观测**：默认 dashboard、告警、SLO 模板、部署标记；
5. **治理**：策略、配额、成本标签、审计；
6. **文档**：README、runbook、ADR 模板、故障排查手册。

黄金路径要像产品一样测试：模板升级后，跑一遍“从零创建 → 部署 → 回滚”的端到端冒烟；否则模板会腐烂。

## 5. Agent-ready 平台

### 5.1 双模接口

| 维度 | 人类 | Agent |
|---|---|---|
| 发现能力 | 门户、搜索、文档 | `llms.txt`、OpenAPI、MCP tool list、能力目录 API |
| 调用 | UI、CLI、IDE | API、MCP、CLI `--json` |
| 认证 | SSO + MFA | OAuth2 client credentials、SPIFFE、短时 token |
| 预演 | 表单校验、dry-run 按钮 | `dry-run` 参数、plan/apply 分离 |
| 错误 | 可读提示 | 稳定错误码 + 结构化 JSON + 修复建议 |
| 审批 | 人工审批 | 危险操作触发审批流，agent 可轮询状态 |
| 证据 | 页面展示 | 返回资源 ID、digest、日志链接、成本 |

### 5.2 机器可读的上下文

Agent 的平台体验，很大程度上取决于“上下文工程”：

- **仓库级**：`AGENTS.md`/`CLAUDE.md` 说明构建、测试、代码规范、禁区；
- **能力级**：OpenAPI/JSON Schema、MCP tool description、示例请求、错误目录；
- **组织级**：服务目录、所有权、SLO、数据分级、成本标签；
- **变更级**：PR 模板、风险评估问卷、回滚步骤。

这些内容应该由平台**生成并校验**，而不是靠人手工维护，否则很快过期。

### 5.3 安全边界

Agent 接入平台后，攻击面从“人点错按钮”扩展到“模型被诱导调用工具”。最低限度：

- 默认只读；写操作按 scope 授权，危险操作（删除、扩权、生产变更）需要人工审批；
- 每个 agent 有独立身份与配额，能追溯到“代表哪个用户/任务”；
- 工具/MCP server 走 allowlist，版本与签名可校验；
- 出口网络限制，敏感数据不出边界；
- 所有 agent 操作进入审计日志，包含输入摘要、工具、结果、成本。

## 6. 组织与运营

### 6.1 团队拓扑

- **Platform team**：以 X-as-a-Service 方式提供能力，负责接口、SLO、路线图；
- **Enabling team**：短期嵌入产品团队，帮助迁移、培训、反馈，避免平台团队变成“外包”；
- **Stream-aligned team**：平台用户，对自己的服务与运行负责；
- **Complicated-subsystem team**：处理特殊子系统（如自研调度器、模型推理引擎）。

平台团队通常需要：平台产品经理、平台工程师、SRE、技术写作者、DevEx/UX。只有工程师的平台，容易做出“能跑但没人用”的东西。

### 6.2 运营机制

- **需求来源**：工单、访谈、遥测、价值流分析，而不是领导拍脑袋；
- **路线图**：季度主题 + 双周迭代；公开 roadmap，标注“研究中/开发中/已上线/将弃用”；
- **支持分层**：文档自助 → 自动诊断 → 人工 on-call；把重复问题转化为自动化；
- **内部营销**：发布说明、demo、office hours、champions、社区频道；
- **反馈闭环**：每季度 NPS/DevEx 调研 + 采用数据分析 + 重点用户访谈。

## 7. 度量

| 类别 | 指标 | 说明 |
|---|---|---|
| 采用 | 活跃团队/开发者、黄金路径覆盖率、能力留存率 | 不是“注册数”，而是“周活跃使用” |
| 激活 | 首次成功时间（time to first deploy/change） | 新团队/新项目从 0 到 1 的时间 |
| 效率 | 申请到交付时延、支持工单量/百团队、重复问题占比 | 平台是否真的减少了等待 |
| 质量 | 变更失败率、事故率、SLO 达成率 | 平台不能只快不稳 |
| 体验 | NPS、DevEx 分维度得分、“如果平台消失会失望吗” | 领先指标 |
| 成本 | 每环境/小时成本、每构建成本、单位请求成本 | 与财务口径对齐 |

**反指标**：能力数量、门户 PV、工单关闭数、文档字数。这些只能说明“平台团队很忙”，不能说明“用户更高效”。

## 8. 90 天落地路线

| 阶段 | 目标 | 交付物 | 成功标准 |
|---|---|---|---|
| 0–30 天 | 找到真实痛点 | 2–3 个高频场景、用户旅程、基线数据 | 能说清“谁在等什么、等多久” |
| 30–60 天 | 打通一条黄金路径 | 脚手架 + 流水线 + 环境 + 可观测 + 文档 | 一个新项目 1 天内上线 dev |
| 60–90 天 | 自助化与护栏 | 门户/API、配额、策略、审计、成本看板 | 80% 请求无需人工；例外可追溯 |
| 90 天+ | 产品化与 agent 化 | 路线图、SLO、MCP/OpenAPI、弃用策略 | 采用率持续上升，DORA/DevEx 改善 |

## 9. 反模式

- **平台即审批队列**：把所有变更收归平台审批，瓶颈从基础设施转移到平台团队；
- **大而全**：一开始就做 20 个能力，结果每个都半成品；
- **只为早期用户定制**：需求被少数团队绑架，后来者无法使用；
- **强制采用**：没有价值支撑的“统一”，只会催生影子系统；
- **门户即平台**：只做 UI，不做自动化与治理，用户点完还是要找人了；
- **共享库耦合**：把复用做成“大家都依赖同一个库”，升级一次全量回归；
- **没有产品经理**：平台团队只对技术负责，不对采用与体验负责；
- **忽视 agent 用户**：只做人类 UI，agent 只能靠爬页面或调用未文档化接口。
