# 平台落地：协作、规范与效果评估

> 平台落地失败，很少是因为“技术做不出来”，更多是因为“没人用、用不好、用了没效果”。平台建设本质上是**组织变革 + 产品运营 + 工程实践**的三合一。

## 1. 先承认：这是组织问题

平台落地涉及四类人，四类人的激励并不天然一致：

| 角色 | 关心什么 | 常见顾虑 |
|---|---|---|
| 研发团队 | 交付速度、少被打扰、可控 | “平台又多一层，出问题找谁？” |
| 测试团队 | 环境、数据、质量门禁 | “门禁太慢，误报太多” |
| 基础设施团队 | 稳定性、成本、安全 | “平台绕过了我们的管控” |
| 管理层 | 投入产出、风险 | “建了平台，指标没变化” |

平台团队如果只从“技术合理性”出发，很容易做出“正确但没人用”的东西。有效的落地，需要同时设计**接口、激励、反馈与度量**。

## 2. 协作模型

### 2.1 团队拓扑

- **Platform team**：以 X-as-a-Service 提供能力，对接口、SLO、路线图负责；
- **Enabling team**：短期嵌入产品团队，做迁移、培训、配对，帮助团队“学会用”，而不是替他们做；
- **Stream-aligned team**：平台用户，对自己的服务与运行负责；
- **Complicated-subsystem team**：处理特殊子系统（调度、推理、存储等）。

平台团队不应成为“所有基础设施请求的审批者”。它的价值在于**把能力做成自助服务**，而不是把专家变成瓶颈。

### 2.2 责任边界

| 活动 | 平台团队 | 研发团队 | 测试团队 | 基础设施 | 安全 |
|---|---|---|---|---|---|
| 平台能力路线图 | A/R | C | C | C | C |
| 黄金路径模板 | A/R | C | C | C | C |
| 服务上线 | C | A/R | C | I | C |
| 生产变更 | C | A/R | I | C | C |
| 测试环境/数据 | A/R | C | R | C | I |
| 安全策略 | C | C | I | C | A/R |
| 事故响应 | C | A/R（服务） | C | R（基础设施） | I |
| 平台度量与复盘 | A/R | C | C | C | I |

> R=负责执行，A=最终负责，C=被咨询，I=被告知。实际组织可按规模调整。

关键原则：**谁拥有服务，谁拥有其运行责任**（you build it, you run it）；平台拥有“能力”，不拥有“用户服务的业务结果”。

## 3. 规范如何落地

### 3.1 规范的生命周期

```
提出 → RFC/ADR → 试点 → 采纳 → 强制执行 → 弃用
```

- **提出**：从真实痛点出发，写清楚“解决什么问题、不解决什么问题”；
- **RFC/ADR**：记录决策背景、备选方案、取舍；ADR 应进仓库，可检索；
- **试点**：选 2–3 个有代表性的团队，设成功标准与时间盒；
- **采纳**：把规范固化进黄金路径/模板/策略，让“正确的方式最容易”；
- **强制执行**：只对高风险/合规项强制，其他用默认值与提示；
- **弃用**：给迁移期、工具支持、到期时间；不允许“永久兼容”。

### 3.2 规范落地的四个杠杆

1. **默认值**：模板/脚手架默认就是合规的，用户不需要读文档；
2. **自动化**：能自动检查的不要靠评审；能自动修复的不要靠人；
3. **可见性**：团队能看到自己的合规/健康分，形成正向竞争；
4. **激励**：把平台采用、工程质量纳入团队目标，而不是只压交付速度。

### 3.3 策略即代码与例外

- 策略用 OPA/Kyverno 等表达，进 Git、有测试、可灰度；
- 例外必须显式：申请人、理由、范围、到期时间、补偿措施；
- 例外到期自动提醒，默认失效；
- 定期审查例外，推动根因修复，而不是“永久白名单”。

### 3.4 培训与社区

- **Onboarding**：新同学第一天能跑通黄金路径；
- **Pairing/Embedded**：enabling team 与产品团队结对，传帮带；
- **Workshop/Dojo**：针对测试、可观测性、安全等主题；
- **Champions**：每个团队培养 1–2 名平台布道者；
- **Community of Practice**：定期分享、答疑、收集需求；
- **文档即产品**：示例可运行、错误可搜索、更新有 owner。

## 4. 如何引入合适的工具

### 4.1 问题优先，工具其次

先回答：

- 我们要改善哪个可度量的结果？（交付时长、故障率、环境等待、成本）
- 现有流程的约束在哪里？（人、流程、工具、权限）
- 不引入新工具，能否通过配置/流程解决？
- 新工具会让谁的工作变重？如何补偿？

### 4.2 评估矩阵

| 维度 | 问题 |
|---|---|
| 契合度 | 是否解决核心问题？与现有栈的集成成本？ |
| 成熟度 | 社区活跃度、版本节奏、生产案例、退出风险？ |
| 安全 | 权限模型、数据流、供应链、合规认证？ |
| 可运维性 | 谁来运维？升级/备份/监控成本？ |
| 锁定 | 数据/API 是否可迁移？有无开源替代？ |
| 成本 | license、云资源、人力、培训、迁移？ |
| 体验 | 学习曲线、文档、错误提示、IDE/CLI 支持？ |
| 生态 | 插件、社区、招聘市场、长期支持？ |

### 4.3 试点与决策

- 2–4 周 spike，验证关键假设（性能、集成、权限）；
- 选一个真实团队、真实项目，设成功标准（如“环境交付从 2 天降到 1 小时”）；
- 试点结束做 go/no-go 决策，明确退出策略；
- 不要用“全员推广”来掩盖试点失败。

### 4.4 避免工具蔓延

- 同类工具收敛到 1–2 个，明确“默认选项”；
- 新工具进入需要架构/平台评审，说明与现有工具的关系；
- 定期清理低使用率工具，降低认知负荷与攻击面；
- 工具数量本身不是能力，**端到端体验**才是。

## 5. AI 工具与 Agent 的引入

AI 工具的引入比传统工具多三个维度：**数据、模型、行为**。

### 5.1 明确 AI 立场

DORA 2025 把“清晰传达的 AI 立场”列为七项能力之一。组织需要明确：

- 允许使用哪些模型/工具？哪些数据可以输入？
- 哪些场景必须人工复核？哪些可以自动执行？
- 代码/内容的知识产权归属与合规要求？
- 成本预算与审批流程？
- 出问题时的责任边界？

含糊的立场会导致“影子 AI”：员工私自使用未授权工具，数据与安全风险更高。

### 5.2 数据与安全

- 数据分级：公开/内部/机密/受限；不同级别对应不同模型与工具；
- 禁止把密钥、PII、客户数据输入外部模型；
- 代码上下文尽量走企业版/私有部署/零保留协议；
- MCP server、插件、skill 走 allowlist，审查权限与数据流；
- Agent 使用独立身份、最小权限、短时凭证、审计。

### 5.3 成本与路由

- 按任务类型路由模型：简单任务用小模型，复杂任务用大模型；
- 设 token/运行时长预算，按团队/工作流归集；
- 缓存常见请求，减少重复调用；
- 监控“每次变更的 AI 成本”，避免“省了人力、涨了账单”。

### 5.4 评估与迭代

- 用真实任务做 A/B：完成时间、返工率、审查负担、缺陷率；
- 不要只看“建议采纳率”，要看“采纳后是否真的更好”；
- 定期复盘 agent 失败案例，形成 prompt/工具/流程改进项；
- 对高风险场景保留人工复核与回滚能力。

## 6. 度量与评估

### 6.1 三层指标

| 层 | 框架 | 指标 | 用途 |
|---|---|---|---|
| 交付 | DORA 5 | 部署频率、前置时间、返工率、失败率、恢复时间 | 判断交付系统是否改善 |
| 体验 | DX Core 4 / SPACE | Speed、Effectiveness、Quality、Impact；满意度、摩擦 | 判断开发者是否更轻松 |
| 平台 | 采用/激活/效率/成本 | 采用率、首次成功时间、申请时延、单位成本 | 判断平台是否被用、是否值得 |

### 6.2 评估方法

- **基线**：改造前先测，避免“感觉变好了”；
- **分层**：按团队画像/业务线/服务类型分组，避免平均值掩盖问题；
- **对照**：试点 vs 非试点、前后对比、同类团队对比；
- **领先 + 滞后**：采用率、首次成功时间是领先指标；DORA、事故率是滞后指标；
- **定性 + 定量**：访谈、观察、问卷 + 遥测数据；
- **价值流**：从需求到上线，找等待时间最长的环节，而不是只看某个工具。

### 6.3 避免虚荣指标

| 虚荣指标 | 问题 | 更好的替代 |
|---|---|---|
| 代码行数 / PR 数 | AI 可以轻易放大 | 变更前置时间、返工率 |
| 平台功能数量 | 不代表被使用 | 活跃采用率、留存 |
| 文档字数 | 不代表可读 | 首次成功时间、文档搜索失败率 |
| 工单关闭数 | 可能只是“关得快” | 重复问题下降、自助解决率 |
| 告警数量 | 可能只是噪音 | 有效告警率、MTTD/MTTR |
| AI 建议采纳率 | 不代表质量 | 返工率、缺陷率、审查负担 |

### 6.4 评估节奏

- **双周**：平台迭代、采用数据、支持问题；
- **月度**：DORA/DevEx 趋势、成本、事故复盘；
- **季度**：平台路线图评审、能力取舍、弃用决策；
- **半年/年度**：组织级效果评估、投入产出、下一阶段目标。

## 7. 四阶段路线图

| 阶段 | 时间 | 目标 | 关键交付 | 成功标准 |
|---|---|---|---|---|
| 0. 发现 | 2–4 周 | 找到约束 | 用户旅程、基线数据、痛点排序 | 能说清“谁在等什么、等多久” |
| 1. 打样 | 4–8 周 | 打通一条黄金路径 | 脚手架 + CI + 环境 + 可观测 | 一个真实项目端到端跑通 |
| 2. 扩展 | 8–12 周 | 自助化与护栏 | 门户/API、配额、策略、审计 | 多数请求无需人工 |
| 3. 优化 | 持续 | 产品化与 agent 化 | SLO、成本、MCP/OpenAPI、路线图 | 采用率与 DORA/DevEx 持续改善 |

每个阶段都要有“退出标准”，避免永久停留在试点。

## 8. 常见阻力与应对

| 阻力 | 背后原因 | 应对 |
|---|---|---|
| “平台是额外负担” | 没看到价值，或迁移成本高 | 先解决最痛的场景；提供迁移工具与 pairing |
| “我们团队特殊” | 平台不够可组合 | 保留逃生通道；把特殊需求变成扩展点 |
| “安全不让” | 策略不透明、审批慢 | 策略即代码、默认安全、例外有期限 |
| “没时间” | 交付压力大 | 把平台能力嵌入现有流程，不额外增加步骤 |
| “AI 不可信” | 质量不稳定、责任不清 | 证据链、人工复核、回滚、明确责任 |
| “指标没变化” | 度量口径不对/滞后 | 分层度量、领先指标、价值流分析 |
| “平台团队是乙方” | 没有产品授权 | 平台即产品、PM 角色、管理层赞助 |

## 9. 检查清单

给平台负责人的 10 个问题：

1. 你的平台用户是谁？他们最痛的一件事是什么？
2. 从申请到第一次成功，需要多久？卡在哪一步？
3. 哪些能力是“必须有人工审批”的？为什么？
4. 黄金路径最近一次端到端验证是什么时候？
5. 平台能力的 owner、SLO、成本是否清晰？
6. 例外有多少？有多少已过期？
7. Agent 能安全地使用哪些能力？如何审计？
8. 你用哪三个指标判断平台是否成功？
9. 哪个能力应该被弃用？迁移计划是什么？
10. 如果明天预算减半，你会保留哪三个能力？
