训练启动与通信：rank、rendezvous 与第一个 collective

结论先行：训练启动不是「容器起来了」，而是三层 membership 依次对齐：Pod 被调度（L1）、进程加入同一个 rendezvous 并拿到 rank/world size（L2）、NCCL communicator 建好且首个 collective 成功（L3）。 三层各有独立的超时和失败文本；把「Pod Running」当成「训练已启动」，是误判 MTTR 的主要原因。

本页以 PyTorch/torchrun 为主干（代码级），对照 TensorFlow 的 TF_CONFIG 与 MPI 的静态进程模型，最后下沉到 NCCL 的 bootstrap/transport/异步错误。所有行号对应 2026-11-23 的快照；PyTorch 当前 main 的 NCCL 后端已重构为 nccl2/，与 2.4–2.8 的行为有差异，文中会标注。

专题导航：总纲 · 工作负载建模 · 启动通信 · 故障自愈 · Checkpoint · RL

一个容易忽略的点：「角色」与「rank」不是同一件事。TF 的 chief 是应用层角色，MPI 的 rank 0 是运行时分配的， PyTorch 的 rank 0 既是运行时 leader、又常被训练脚本当成 checkpoint owner。编排层如果把这三者混为一个字段， 恢复时就会出错。

二、PyTorch 路径

2.1 torchrun 到底做了什么

torchrun 是一个进程管理器 + rendezvous 客户端，不是训练框架的一部分。它做四件事：

  1. 解析 --nnodes、--nproc-per-node、--rdzv-backend、--rdzv-endpoint、--max-restarts 等参数。
  2. 创建 LocalElasticAgent，为每个节点启动一个 agent 进程。
  3. 通过 rendezvous 拿到本轮的 (store, rank, world_size, bootstrap_store_info)。
  4. 为每个 worker 组装环境变量并 fork/spawn；监控 worker 状态，失败或成员变化时重启 worker group。

关键默认值（代码确认）：

  • --nnodes 默认 "1:1"，格式是 MIN:MAX；MIN != MAX 即弹性区间。
  • --nproc-per-node 默认 "1"，可为 auto/cpu/gpu/xpu/int；它决定 LOCAL_WORLD_SIZE，也是唯一被限制为 「全作业同构」的量。
  • --rdzv-backend 默认 "static"（用 --master-addr/--master-port/--node-rank，不支持弹性）； c10d 是推荐后端；--max-restarts 默认 0（不自动重启）。
  • --standalone 强制 c10d + localhost:0 + 随机 UUID，并忽略显式 rdzv 参数；static 且未给 endpoint/master-port 且 nnodes 上限为 1 时，也会降级到 c10d localhost:0。
  • MASTER_PORT 的最终兜底是 29500，只对 static 有意义；c10d 的端口在 rdzv endpoint 里。

Agent 把 rendezvous 结果变成 worker 环境变量：RANK、GROUP_RANK、ROLE_RANK、ROLE_NAME、LOCAL_WORLD_SIZE、 WORLD_SIZE、GROUP_WORLD_SIZE、ROLE_WORLD_SIZE、MASTER_ADDR、MASTER_PORT、TORCHELASTIC_RESTART_COUNT、 TORCHELASTIC_MAX_RESTARTS、TORCHELASTIC_RUN_ID、TORCHELASTIC_USE_AGENT_STORE。LOCAL_RANK 单独写： virtual_local_rank=True 时每个 worker 只看到自己那张卡（CUDA_VISIBLE_DEVICES 收窄为单卡、LOCAL_RANK=0）。

两个反直觉点：

  • TORCHELASTIC_RESTART_COUNT 是已用掉的次数，不是剩余次数（restart_count = max_restarts - remaining_restarts）。
  • torchrun 会给 worker 注入 TORCH_NCCL_ASYNC_ERROR_HANDLING=1（若用户没设）；而 PyTorch 库层默认是 3 （SkipCleanUp）。这会影响 NCCL 出错时是杀进程还是只清理 communicator，排查时不要假设两者一致。

2.2 rendezvous：成员协商与 quorum

Rendezvous 的接口契约是：next_rendezvous() 阻塞直到本轮成形/被关闭/超时；num_nodes_waiting() 返回「到晚了、 在等下一轮」的节点数；set_closed() 的传播是最终一致的，不能当同步原语。

RendezvousInfo 携带四样东西：控制面 store、组内 rank、world_size、bootstrap_store_info。 RendezvousStoreInfo.build() 由 rank 0 选一个空闲端口/地址并写入 store 的 MASTER_ADDR/MASTER_PORT 两个 key， 其余 rank 从 store 读。这解释了一个常见困惑：--rdzv-endpoint 只指定 rendezvous 服务器，不一定是训练进程的 master 地址；后者是 rank 0 在 rendezvous 后写进 store 的。

c10d 后端的落地细节：

  • TCPStore 端点默认端口 29400，read_timeout 默认 60s。
  • 状态 key 是 "torch.rendezvous." + run_id，值是 pickle 后的整份 _RendezvousState。因为 store 的 get 会阻塞， 实现先 compare_set(key, "", "Y2FuaW1hZGFt") 塞一个哨兵值，读到哨兵即视作 None。
  • 写入用 compare_set(key, token, new_state) 做 CAS；store 的 compare_set 不返回「是否成功」，实现用 「本地状态与远端状态逐字节比较」来推断。

关于 TryCreate/Join：当前 dynamic rendezvous 没有名为 TryCreate 的函数。create 语义由第一次 compare_set（从空值到哨兵）承担；join 语义由 _RendezvousJoinOp 返回的 action 表达： ADD_TO_PARTICIPANTS → ADD_TO_WAIT_LIST/ADD_TO_REDUNDANCY_LIST → MARK_RENDEZVOUS_COMPLETE。 try_create_rendezvous() 这个名字只保留在 etcd legacy handler 里。

轮次完成条件是理解「启动慢」的关键：

  • 参与数达到 max_nodes → 立即完成。
  • 否则等到 min_nodes 后再等 last_call（默认 30s）才封轮。
  • 所以 --nnodes=4:8 在只有 4 个节点时会稳定地多等 30s，这不是 hang。
  • keep-alive 默认 5s 一次、最多 3 次失败；约 15s 收不到心跳就把节点从 participants/wait_list 剔除。
  • 失败表现：连不上 rdzv store → RendezvousConnectionError；等人超时 → RendezvousTimeoutError； 作业已关闭 → RendezvousClosedError；状态反序列化失败 → RendezvousStateError。

re-rendezvous 的能力边界：torchrun 的做法是杀掉全部本地 worker，重新走一次 next_rendezvous()，用新 rank/world size 重新启动进程。而训练脚本里的 init_method="env://" 本身是一次性的——_env_rendezvous_handler 在 yield 之后直接 raise RuntimeError("Unable to perform re-rendezvous using env:// method")。 弹性来自 agent，不来自 process group。这也是为什么「在训练脚本里自己调 init_process_group」无法获得弹性。

2.3 init_process_group：默认不做全员 barrier

两种初始化方式：显式 store+rank+world_size，或 init_method（默认 env://）；两者互斥。

env:// 硬性要求 RANK、WORLD_SIZE、MASTER_ADDR、MASTER_PORT，缺任何一个都直接抛 env:// rendezvous: environment variable X expected, but not set；store 由 rank 0 做 server、其余做 client。

几个关键语义：

  • 默认 timeout：非 NCCL 30 分钟（kProcessGroupDefaultTimeout = 30*60*1000ms），NCCL 10 分钟 （kProcessGroupNCCLDefaultTimeout = 10*60*1000ms）。
  • store-based barrier 默认不执行：只有 TORCH_DIST_INIT_BARRIER=1 时才走 _store_based_barrier。也就是说 init_process_group 可能在其他 rank 还没到齐时就返回；真正的全员同步发生在第一个 collective 或显式 barrier()。 这是「初始化看起来很快，但第一个 allreduce 卡住」的常见原因。
  • backend 选择：显式 backend 优先；只给 device_id 则查 Backend.default_device_backend_map （cuda→nccl、cpu→gloo、xpu→xccl）；两者都没有则懒初始化。也支持 "cpu:gloo,cuda:nccl" 多后端字符串。
  • device_id 会立即建 NCCL communicator（ncclCommInit*，而非懒建），子组尽量用 ncclCommSplit。 「想尽早暴露 NCCL 初始化错误」正是它的用途。
  • new_group 的关键约束：所有 world rank 都必须调用（即使不是成员），且调用顺序必须一致；非成员返回 NON_GROUP_MEMBER；device_id 同样触发 eager init。

store 前缀是三层叠加：PrefixStore("default_pg", store) → PrefixStore(f"{group_name}/", ...) → PrefixStore(f"{device}/", ...)。所以「同一个 store、多个 group、多个 backend」不会撞 key；排查时 store 里看到的 key 长成 default_pg/<group>/cuda/...。

2.4 NCCL communicator 初始化

PyTorch 当前 main 的 NCCL 后端已重构到 nccl2/（后端名 nccl，另有 nccl-legacy）。构造时读两个关键开关： TORCH_NCCL_ASYNC_ERROR_HANDLING（默认 SkipCleanUp=3）与 TORCH_NCCL_BLOCKING_WAIT（默认 false）。

uniqueId 的传播（代码确认，取代老的 _broadcastUniqueId 路径）：

  1. NCCLBootstrap 按 TORCH_NCCL_RANKS_PER_ROOT（默认 128）把 rank 分块。
  2. 块首 rank 调 ncclGetUniqueId()，把 128 字节写入 PrefixStore(group_name) 下的 key nccl_storekey_<generation>。
  3. 其余 rank store->wait(keys, timeout) 后 multiGet。
  4. 块数 >1 时走 ncclCommInitRankScalable（多 root 的 uniqueId 数组），否则 ncclCommInitRankConfig。

这句 store->wait(keys, timeout_) 的 timeout 就是 process group 的 timeout（NCCL 默认 10 分钟）： root 卡住 → 其他 rank 在 comm init 里静默等 10 分钟，然后报 Failed to initialize NCCL communicator。 createNcclComm 失败时还会 commAbort 一次，避免半成品 communicator 泄漏。

未显式给 device 时，device 由 rank % device_count 推断——多进程共享 GPU 或 CUDA_VISIBLE_DEVICES 配错时， 这一步会静默把多个 rank 绑到同一张卡上，随后 NCCL 才报错或死锁。

watchdog：!blocking_wait_ 时启动 timeout_thread_；线程每 1s 醒一次，先 checkWorkQueue()（garbageCollect 判定 work 超时/出错），再 commGetAsyncError() 探测 communicator 级异步错误，命中后 handleWatchdogFailure() 按 async error 模式决定 abort comm / 杀进程。

TORCH_NCCL_ENABLE_MONITORING（默认 1）与 TORCH_NCCL_HEARTBEAT_TIMEOUT_SEC（默认 480s）在文档里被标为 nccl-legacy only；当前 nccl 后端没有独立 heartbeat 线程，唯一轮询者是上面的 1s watchdog。 TORCH_NCCL_BLOCKING_WAIT / TORCH_NCCL_ASYNC_ERROR_HANDLING 在本 commit 都没有标注 deprecated； BLOCKING_WAIT 默认 0，ASYNC_ERROR_HANDLING 默认 3、torchrun 注入 1。不同版本行为不同，不要写死。

两个容易归因错误的点：

  • 窗口 8 的「卡住」不是死锁而是 timeout：store->wait(keys, timeout) 的 timeout 就是 PG timeout，job 会先安静 10 分钟再统一报错。把 init_process_group(timeout=...) 调小可以显著缩短 MTTR。

三、TensorFlow 路径

TF_CONFIG 是一个 JSON 字符串，只有两个顶层字段：cluster（全集群一致）与 task（每进程不同）。 cluster 是 job 名 -> [host:port, ...] 的字典；task 是 {"type": ..., "index": ...}。合法 role 为 chief/worker/ps/evaluator，只有 ParameterServerStrategy 才应该有 ps。

职责划分：

  • worker 干实际训练，worker 0 常常兼任 chief。
  • chief 额外负责存 checkpoint、写 TensorBoard summary。
  • ps 只为参数服务器策略提供参数存储。
  • evaluator 算评估指标。
  • 「index 0 被指定为 chief」不是约定，而是 tf.distribute.Strategy 的实现方式；如果显式定义了 Chief， 则以 Chief 为准。

MultiWorkerMirroredStrategy 的建组方式：每个 worker 跑同一份程序，TFConfigClusterResolver 从 TF_CONFIG 读 task_type/task_id 与各 task 地址；strategy 用 cluster_resolver.num_accelerators() 决定用几张卡， 所有 worker 的卡数必须一致，否则行为未定义。它有两套集合通信实现：CommunicationImplementation.RING （基于 RPC/gRPC，CPU/GPU 都支持）与 CommunicationImplementation.NCCL（仅 GPU）。

一个反直觉但很重要的点：所有 tf.distribute 与非 tf.distribute API 都可能内部发起 collective，包括 checkpoint/save（读 ON_READ 变量会触发 all-reduce）。因此不能只让一个 task 跑训练循环；官方建议每个 worker 跑完全相同的程序，并明确说「按 task_type/task_id 分派是 error-prone 的」。这也是 chief checkpoint 的实际做法： chief 写到正式 model dir，非 chief 写到临时目录后删除；「只有 chief 那份才是权威」，但所有 worker 都必须参与 save 的 collective。

TF 没有 torchrun 式内建弹性：文档描述的是「某个 worker 被打断，整个集群暂停直到它重启，其他 worker 也会重启并 重新加入集群，然后各自从上次 checkpoint 恢复」。K8s 上这件事由 Training Operator（v1）的 TFJob 承担： restartPolicy（Always/OnFailure/ExitCode/Never）按副本类型配置，chief/worker/ps 的退出码决定是否重拉； cleanPodPolicy 决定作业结束后删哪些 Pod。官方教程把容错恢复指向 BackupAndRestore，而不是 ModelCheckpoint。

TFJob（legacy v1）如何把这些角色落到 K8s 对象上：

  • TFReplicaSpecs 的 key 是 Chief/Worker/PS/Evaluator/Master；Chief 与 Master 语义等价，Master 只是为兼容旧配置保留。如果有 Chief，它就是 chief；否则 worker:0 是 chief。
  • PS 只在 ParameterServerStrategy 下使用；Evaluator 只做评估，不参与训练循环。
  • Operator 按 rtype/index 生成 TF_CONFIG，并只注入名为 tensorflow 的默认容器；cluster 里包含所有角色的地址。 所以「容器里没有 TF_CONFIG」通常不是 TF 的问题，而是副本类型/容器名不匹配。
  • 每个 replica 的 restartPolicy 独立：PS 可以 Always，chief/worker 用 OnFailure；successPolicy: AllWorkers 是 v1 的成功条件（不是 JobSet 的 All/Any），语义是「所有 worker 成功」。
  • 没有 re-rendezvous：Pod 重启后从 checkpoint 恢复，整个集群会暂停/重启；不要把 torchrun 的 elastic 语义套到 TFJob 上。

四、MPI 路径

MPIJob 的进程模型是 launcher + worker 两组 Pod：

  • worker 默认只跑 sshd -De，负责被 rsh 进去起 rank。
  • launcher 是一个普通 batchv1.Job，用户在它的 command 里自己写 mpirun/mpiexec。
  • hostfile 由 operator 生成：OpenMPI 是 <pod>.<job>.<ns>.svc[.<clusterDomain>] slots=N，Intel MPI/MPICH 是 <host>:N；每行 slots 取 spec.slotsPerWorker（默认 1）。runLauncherAsWorker=true 时 launcher 自己也会出现在 hostfile 第一行。
  • launcher 侧环境变量决定 mpirun 去哪找 hostfile：OpenMPI 用 OMPI_MCA_orte_default_hostfile、 OMPI_MCA_orte_keep_fqdn_hostnames=true、OMPI_MCA_plm_rsh_args=-o ConnectionAttempts=10；Intel 用 I_MPI_HYDRA_HOST_FILE，MPICH 用 HYDRA_HOST_FILE。
  • -np 不是 operator 注入的：示例里由用户写 mpirun -np 2 ...。rank 总数由 -np（显式）或「所有 slots 之和」 （隐式）决定，与 Worker.replicas * slotsPerWorker 不一致时，要么少起 rank，要么撞上 oversubscribe 限制。
  • rank 相关环境变量来自 MPI 运行时：OpenMPI 提供 OMPI_COMM_WORLD_RANK/SIZE/LOCAL_RANK/LOCAL_SIZE/NODE_RANK； MPICH 的 PMI 常见 PMI_RANK/PMI_SIZE，PMIx 体系是 PMIX_RANK。

为什么 MPI 不能像 torchrun 那样 re-rendezvous：

  • MPI_Init 的 world model 是「在一个 MPI 进程生命周期内至多初始化一次」，MPI_COMM_WORLD 的成员在 MPI_Init 时就固定。
  • 唯一的「加人」途径是 MPI_Comm_spawn：子进程有自己的 MPI_COMM_WORLD，父进程通过 intercommunicator 通信； 这是「新增一个组」，不是「把现有 MPI_COMM_WORLD 扩容」。
  • 因此 MPIJob 的「重启」只能是 Kubernetes 语义：launcher Job 失败 → BackoffLimit/restartPolicy 决定重拉； worker 挂掉 → 该 Pod 按 restartPolicy 重建，但 launcher 侧的 mpirun 会话已经断了，整轮 rank 映射要重来。
  • launcherCreationPolicy: WaitForWorkersReady 的存在就是为了先让 worker 全部 Ready 再起 launcher，避免 「launcher 先到、worker 没 DNS」。

五、NCCL 内部：bootstrap、拓扑与异步错误

bootstrap 由 uniqueId 承载：ncclBootstrapHandle 只有三个字段——magic、监听地址 addr、nRanks， 它被塞进 128 字节的 ncclUniqueId。ncclGetUniqueId 在非 NCCL_COMM_ID 模式下随机生成 magic、填入本机 bootstrap 网卡地址，然后 bootstrapCreateRoot() 当场 listen（后台线程 accept）。所以 uniqueId 里带的是 「第一个 root 的 IP:port」。

bootstrap 的连接建立不是「全员连 root」：每个 rank 先建自己的 listen socket，把自己的联系方式发给所属 root， root 回给它「环上的下一个 peer」，随后两两 socketRingConnect；最后通过这个环 all-gather 所有 rank 的 proxy 地址与 P2P 地址。所以 bootstrap 阶段任何一个 rank 不可达，表现都是「连接 root 超时/收到残缺环」，而不是一条明确的 「rank N 挂了」。

拓扑与算法：init 时先 ncclTopoComputePaths，再分别搜索 ring（NCCL_TOPO_PATTERN_RING）与 balanced tree （NCCL_TOPO_PATTERN_BALANCED_TREE），可选 collnet/nvls；comm->nChannels = min(tree, ring)，然后通过 bootstrapAllGather 把各 rank 的 graph 信息对齐，再按 channel 建连。

P2P 选择：ncclTopoCheckP2p 先看 hostHash（不同主机直接不 P2P），再看 shmDev（同一个 /dev/shm 才能用 CUDA IPC/shm 传输）；然后比较 PCI 路径类型与 NCCL_P2P_LEVEL（默认 PATH_PXB），用户可用 NCCL_P2P_DISABLE/NCCL_P2P_LEVEL 覆盖。跨 Pod 但同机、且没共享 IPC namespace 时，shmDev 不同 → 同机流量也会退回网络，这是 K8s 上「明明同机却只有 socket 带宽」的根因之一。

传输与 proxy：节点内优先 NVLink/CUDA P2P，其次 shm（POSIX shm + CUDA IPC），节点间走 net 插件（IB verbs / socket）；需要网络参与时由 proxy 进度线程推进，proxy 的并发度也是常见调优点。

collective 的异步语义：ncclAllReduce 这类带 stream 的函数只要把操作「压到 stream 上」就返回 ncclSuccess， 之后的错误只能通过 ncclCommGetAsyncError 观测；一旦 communicator 出错，已入队操作的完成性和正确性都不再有任何 保证，正确做法是 ncclCommAbort 后重建。

六、把超时设在正确的层

启动慢/卡住时，先确认「卡在哪一层」，再调对应的超时；只调大 K8s 的 activeDeadlineSeconds 会把问题拖长：

层超时/参数默认值调小的影响
Pod 调度Kueue waitForPodsReady、Volcano scheduleTimeoutSeconds依配置更快失败，但可能误杀慢启动
rendezvousRendezvousTimeout.join（--rdzv-conf）600s更快报 RendezvousTimeoutError
rdzv storeTCPStore read_timeout60s更快暴露网络/端口问题
process groupinit_process_group(timeout=...)NCCL 10min / 其他 30min更快暴露缺 rank/NCCL 初始化失败
NCCL watchdog同上（PG timeout）10min更快 abort，但可能误杀慢节点
作业activeDeadlineSeconds无兜底，不能替代上面几层

一个实用原则：把「成员到齐」的超时设得比「单次 collective」短。例如 rendezvous join 2–5 分钟、 PG/NCCL 10–20 分钟、作业 deadline 数小时。这样缺一个 rank 时，几分钟内就会失败并进入重试，而不是安静地等 半小时。
