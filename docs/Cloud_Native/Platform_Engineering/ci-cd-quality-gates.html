CI/CD 与自动化质量保障：从流水线到证据链

CI/CD 的目标没有变：让变更以可预测的方式、尽可能小的批量、可验证地到达用户，并且随时能退回来。Agent 时代的变化是：变更的供给量变大、非确定性变强，因此“证据”必须比“审批”更可靠。

1. 四个不变量

  1. 一次构建，多次部署：制品只构建一次，靠 digest 晋级，禁止“在环境里重新构建”。
  2. 流水线即代码：定义与代码同仓、同审查、同版本；pipeline 的变更也要被测试（参见 DevOps 理念与实践）。
  3. 小批量、短分支、频繁集成：变更越小，验证越便宜，回滚越容易。
  4. 每个门禁都有 Owner、有证据、有例外流程：没有 owner 的门禁最终会变成“点一下通过”。

3. 构建：可复现是信任的起点

  • 固定工具链：编译器、基础镜像、依赖版本全部锁定；禁止“latest”。
  • Hermetic build：构建过程不依赖外部网络与宿主状态；依赖走内部代理/镜像。
  • 可复现性验证：同一 commit 两次构建应得到相同 digest（或可解释的差异）。
  • 缓存要有边界：远程缓存命中率是效率指标，但缓存投毒是攻击面；缓存 key 要包含依赖哈希与工具版本。
  • 构建环境即代码：runner 镜像、系统依赖、环境变量都版本化。

对 AI 应用，构建产物不止容器镜像，还包括：prompt 包、评测集、索引快照、模型/适配器版本。它们应进入同一套版本与签名体系。

4. 制品与供应链证据链

4.1 制品管理

  • 不可变：制品一旦发布不可覆盖；用 digest 而非 tag 引用。
  • 可追溯：制品能反查到 commit、构建任务、构建者、依赖清单。
  • 可治理：保留策略、复制/同步、垃圾回收、漏洞扫描、下载审计。
  • 可准入：集群侧 admission 只允许“已签名 + 有 SBOM + 无高危漏洞”的镜像运行。

4.2 供应链证据

证据回答的问题标准/工具
SBOM这个制品由哪些组件构成？CycloneDX、SPDX
Provenance它在哪、由谁、用什么构建？SLSA、in-toto
签名它是否被篡改？Sigstore/Cosign、KMS
扫描报告已知漏洞与许可证风险？Trivy、Grype、SCA
VEX漏洞是否实际可利用？VEX
审批记录谁批准了这次发布？发布系统/工单

SLSA Build 的 L1–L3 可以作为一个渐进路径：L1 有 provenance；L2 由托管构建平台生成签名 provenance；L3 强化构建平台，防篡改。大多数团队应从“L2 + 准入校验”开始，而不是一步追求 L3。

4.3 发布证据包

把一次发布所需的证据固化为一个可归档的清单，既方便审计，也方便事故复盘：

# 示意：release-evidence.yaml
release:
  service: checkout-api
  commit: 9f2c1ab
  artifact: registry.example.com/checkout-api@sha256:...
  sbom: sbom.cdx.json
  provenance: provenance.intoto.jsonl
  signature: cosign.sig
  tests:
    unit: { passed: 812, failed: 0 }
    contract: { passed: 24, failed: 0 }
    e2e: { passed: 18, failed: 0 }
  security:
    critical: 0
    high: 2        # 已评估，VEX 标记为 not_affected
  evals:           # LLM 应用适用
    suite: checkout-assistant-v3
    pass_rate: 0.94
    regression: -0.01
  approvals:
    - role: service-owner
      by: alice
      at: 2026-11-20T10:12:00Z
  deploy:
    env: prod
    strategy: canary
    started_at: 2026-11-20T10:30:00Z

这份清单不需要一开始就全有；可以从“commit + digest + 测试报告 + 审批”四项开始，逐步补齐。

5. 测试体系：从金字塔到“证据组合”

测试金字塔仍然有效，但不必教条。关键是测试分层与反馈速度匹配：

层级运行时间覆盖什么失败时
单元秒级纯逻辑、边界阻断，开发者立即修
组件/集成分钟级DB、消息、外部依赖契约阻断，定位到组件
契约分钟级服务间协议阻断，通知提供方/消费方
E2E十分钟级关键用户旅程阻断晋级，允许重试但不掩盖 flake
探索/混沌小时级韧性、故障注入不阻断日常，进入改进 backlog

几个容易被忽视的工程细节：

  • 测试影响分析（TIA）：只跑受变更影响的测试，缩短反馈；但要有“定期全量”兜底，防止漏测。
  • Flaky 治理：flaky 测试必须隔离、有 owner、有修复 SLA；flaky rate 是测试基础设施的核心指标。
  • 测试数据管理：固定 fixture、按需生成、脱敏、可重置；测试数据是平台能力，不是每个团队的私事。
  • 契约测试：微服务/多团队场景下，比端到端更便宜、更早发现问题。
  • 变异测试：对关键模块（计费、权限、风控）验证“测试是否真的能抓到 bug”。
  • 覆盖率是代理指标：高覆盖率不等于高质量；关键是关键路径与失败路径是否被覆盖。

6. LLM/AI 应用的质量保障

传统测试假设“同样输入得到同样输出”。LLM 应用打破了这个假设，因此需要一套新的质量体系：eval-driven development。

6.1 评测的四个层次

层次做什么何时跑产物
单元级 eval单条 prompt/工具调用的正确性每次提交通过率、失败样例
离线回归 eval黄金集上的整体质量每次 PR/每日报告、与基线的 delta
在线 eval生产流量的抽样评估持续质量分、漂移告警
红队/对抗 eval注入、越权、泄露、滥用发布前/定期风险清单、修复项

6.2 评测集与判定

  • 黄金集：覆盖核心意图、边界、长尾、对抗样本；版本化、可追溯来源。
  • 判定方式：规则断言（格式、引用、工具调用）优先；LLM-as-judge 用于主观质量，但必须用人工标注校准，并监控 judge 与人的一致性。
  • 回归阈值：不是“分数越高越好”，而是“相对基线不能显著下降”；对关键切片（如退款、医疗建议）设更严格的阈值。
  • 成本与延迟也是质量属性：把 token 成本、首 token 延迟、端到端延迟纳入 eval 报告。

6.3 质量维度

维度问题方法
正确性答案对不对？黄金集、规则断言、人工抽检
忠实性是否忠于检索到的证据？引用校验、groundedness eval
安全性是否泄露、越权、被注入？红队、guardrail 测试、PII 扫描
鲁棒性输入扰动下是否稳定？改写、噪声、多语言、边界输入
工具使用是否调用了正确的工具/参数？trace 断言、mock 工具
成本/延迟是否在预算内？token/时延基线、压测

6.4 让 eval 成为门禁

  • PR 级：eval delta 超过阈值 → 阻断合并；失败样例自动附在 PR 评论。
  • 发布级：金丝雀阶段对比新旧版本的在线指标（质量分、投诉率、转人工率），异常自动回滚。
  • 模型/prompt 变更：必须走与代码相同的 review、版本与回滚流程；模型版本要 pin，不能“自动跟随最新”。

判断：LLM 应用最危险的不是“模型变笨”，而是“质量在无人察觉的情况下缓慢漂移”。在线 eval + 基线告警比一次性上线评测更重要。

7. 质量门禁：从“审批”到“风险分级 + 策略”

7.1 风险分级

风险级别示例门禁
低文档、样式、非关键内部工具自动化检查通过即可合并
中一般业务逻辑自动化 + CODEOWNERS 评审
高认证、支付、数据删除、基础设施自动化 + 双人评审 + 安全扫描 + 金丝雀
极高生产数据库迁移、权限模型变更变更窗口 + 人工审批 + 回滚预案 + 观察期

分级标准要写进策略，而不是靠评审人临场判断。

7.2 策略即代码

  • 用 OPA/Kyverno 表达“什么可以做”：镜像必须签名、必须来自可信仓库、必须有资源限制、必须打成本标签；
  • 策略要有测试：像代码一样单测、dry-run、灰度；
  • 例外必须显式：谁批、为什么、什么时候到期；到期自动提醒/失效；
  • 门禁要可观测：阻断率、误报率、平均等待时间；误报率高的门禁会被绕过。

7.3 门禁的“证据优先”原则

一个门禁只有两种合法状态：通过（有证据） 或 不通过（有原因）。不允许“人工点一下通过但没有记录”。证据包括：测试报告、扫描结果、SBOM、签名、eval 报告、审批记录、回滚演练记录。

8. 发布与回滚

8.1 发布策略

策略适用优点注意
滚动更新大多数无状态服务简单、资源省需要就绪探针与优雅退出
蓝绿需要快速切换回滚快双倍资源、数据兼容
金丝雀高风险变更影响面可控需要指标分析与自动决策
特性开关功能级灰度解耦部署与发布开关债务、清理机制

8.2 GitOps 与漂移检测

  • 期望状态在 Git；集群状态由 controller 持续 reconcile；
  • 任何手动变更都会被纠正——这既是优点，也是事故时的风险（需要 break-glass 流程）；
  • 漂移告警要能区分“合法漂移”（如 HPA 副本数）与“非法漂移”。

8.3 数据库变更

  • 采用 expand/contract：先加字段/双写，再迁移，最后删旧字段；
  • 迁移脚本必须可重入、可回滚（或至少可前滚）；
  • 生产迁移先在影子库/只读副本验证；
  • 大表变更考虑在线 DDL 工具与锁影响。

8.4 回滚是功能，不是事故

  • 回滚脚本/按钮要定期演练；未演练的回滚等于没有；
  • 回滚决策要有明确阈值（错误率、延迟、业务指标）；
  • 回滚后要保留现场（日志、trace、指标快照）；
  • 数据库/消息/缓存的回滚边界要提前写清楚（有些变更不可回滚，只能前滚）。

9. Agent 进入流水线

9.1 适合交给 agent 的任务

  • 失败分析：CI 失败日志聚类、定位可疑 commit；
  • 测试生成：补充边界用例、回归用例（需人工审查测试意图）；
  • 依赖升级：批量升级 + 自动修复 + 跑测试；
  • 文档同步：API 变更后更新文档；
  • 代码审查：风格、常见缺陷、安全模式；
  • Issue 分诊：分类、复现步骤提取、指派。

9.2 不适合默认放行的任务

  • 生产变更审批、权限提升、密钥操作；
  • 安全关键路径的自动合并；
  • 大规模重构/删除；
  • 跨仓库的强制推送。

9.3 工程化护栏

以 GitHub Agentic Workflows 为例，它体现了一组可复用的模式：

  • 自然语言定义 → 标准流水线：Markdown 编译为 Actions YAML，复用现有 runner 与策略；
  • 默认只读：agent 不能直接写仓库；
  • 沙箱 + 防火墙：容器内执行，出口受控；
  • safe outputs：agent 的产出经过校验后才落地；
  • threat detection：独立 job 扫描变更中的可疑内容；
  • 隔离升级：高风险场景使用 micro-VM/独立环境。

落地时至少补齐：

  1. Agent 身份：独立 service account、短时 token、按任务 scope；
  2. 来源标注：AI 生成的 commit/PR 打标，便于复盘与统计；
  3. 风险路由：触碰敏感路径的 PR 强制人工评审；
  4. 小批量：限制单 PR 变更行数/文件数，超过阈值自动拆分或要求说明；
  5. 审计：记录 agent 的输入、工具调用、输出、成本；
  6. 预算：按团队/工作流限制 token 与运行时长。

9.4 CI 的新攻击面

  • 不可信 PR 触发 workflow：pull_request_target + 检出 PR 代码 = 高危组合；
  • 缓存/制品投毒：低权限 job 写入的缓存被高权限 job 使用；
  • 依赖混淆：内部包名被公共仓库抢注；
  • 提示注入：issue/PR 正文、代码注释、README 中的恶意指令影响 agent；
  • MCP/工具供应链：第三方 tool server 可能被篡改或过度授权；
  • 密钥外泄：agent 把 secret 写进日志、PR 或外部请求。

对策：最小权限、OIDC 短期凭证、环境隔离、出口白名单、不可信输入不进入高权限上下文、对 agent 输出做 secret 扫描。

11. 落地清单

  • 统一流水线模板，禁止“每个团队一套 YAML”；
  • 固定工具链与基础镜像，构建可复现；
  • 制品不可变 + 签名 + SBOM + provenance；
  • 集群准入只允许可信制品；
  • 测试分层、flaky 隔离、关键路径契约测试；
  • 风险分级门禁 + 策略即代码 + 例外到期；
  • GitOps + 金丝雀 + 自动回滚 + 回滚演练；
  • LLM 应用接入离线/在线 eval 与红队；
  • Agent 任务默认只读、沙箱、审计、预算、来源标注；
  • 发布证据包可归档、可查询、可追溯。
