Volcano 调度器：Session、Action 与队列模型

Volcano 把「批作业调度」做成了一套与 kube-scheduler 平行的调度器：它自己维护作业快照、自己做节点筛选与打分、自己向 apiserver 发 Bind。 本页回答三个问题：一次调度回合（Session）里状态是怎么组织的；Action 管线为什么必须是那个顺序；Statement 事务和原生 assume 到底差在哪。 对象模型、gang 门槛、队列权益、主要 action 和插件都会逐个落到代码上；Kueue 的准入模型、DRA allocator 的内部算法不在本页展开（分别见 kueue.md 与 scheduling-strategy.md）。

版本基线：Volcano v1.16.1，commit a254367（仓库 .repos/upstream/volcano）。 文中的默认值、状态机、回调语义都来自该 commit；调参建议会明确标注为经验判断。官方文档站为 “Latest”（v1.16.x）分支，与代码基线同代。

一、组件边界：谁创建对象、谁选点、谁 Bind

Volcano 不是一个「extender」：它不是把节点选择结果交给 kube-scheduler 去 bind，而是直接充当名为 volcano 的 scheduler。三个常驻组件分工如下。

组件负责不负责
vc-scheduler监听 Pod/PodGroup/Queue/HyperNode；周期性 OpenSession；按配置顺序执行 Action；用插件做 predicate 与打分；Pods().Bind 写回绑定不创建 Job/Pod、不生成 Pod 模板、不改 workload 控制器语义
vc-controller-managerJob/PodGroup/Queue/JobFlow/CronJob 等控制器；创建 PodGroup、按 PodGroup 状态创建 Pod、维护 Queue 状态不参与节点选择（syncJob 只按 PodGroup phase 决定是否建 Pod）
vc-webhook-managerPod/PodGroup/Queue/Job 的 mutate 与 validate：按资源组配置注入 schedulerName/label/affinity/toleration、可选 scheduling gate；校验 queue 是否存在且 Open、拓扑字段是否互斥不做配额准入（那是 enqueue action 的职责）

三者的连接点有两处，都值得记住：

  1. 调度权按 schedulerName 切分。Volcano 的 cache 只接受 SchedulerName 在 --scheduler-name 列表里的 Pod（可重复的 StringArray，默认 volcano），否则连 JobInfo 都不会创建（options.go#L181、event_handlers.go#L72-L82）。所以 kube-scheduler 不会去调度 schedulerName: volcano 的 Pod，Volcano 也不需要 kube-scheduler 帮它算节点。
  2. Bind 由 Volcano 自己发。DefaultBinder.Bind 逐 Pod 调 CoreV1().Pods(ns).Bind(&v1.Binding{...})，把 Target.Name 设为选中的节点（cache.go#L245-L266）。这和 kube-scheduler 的 defaultBinder 用的是同一个 API，但实例、队列、重试语义完全不同。
flowchart LR
    U["用户 / 上层编排"] -->|创建| A["apiserver"]
    A -->|watch| CM["vc-controller-manager<br/>Job/PodGroup/Queue 控制器"]
    A -->|watch| WH["vc-webhook-manager<br/>mutate / validate"]
    A -->|watch Pod/PodGroup/Queue| S["vc-scheduler"]
    CM -->|创建 PodGroup / Pod| A

    S -->|"Session: Action + Statement"| B["Bind 队列"]

    S -.->|"CloseSession 写 PodGroup status"| A

一个容易被忽略的因果链：enqueue 把 PodGroup 从 Pending 改为 Inqueue 之后，Job 控制器才会创建 Pod（job_controller_actions.go#L439-L444）。 也就是说 Volcano 的「准入」不是软性的排队，而是直接决定集群里有没有这些 Pod。这一点与 Kueue 的 admit/stop 在效果上相近，但 Volcano 把它做在调度器的一个 action 里，而不是独立控制器里。

二、对象模型：Job → PodGroup → Pod，Queue 是另一条轴

Volcano 的调度单元是 PodGroup，不是单个 Pod。三者关系是：

Volcano Job (batch.volcano.sh/v1alpha1)
  └─ ownerReference → PodGroup (scheduling.volcano.sh/v1beta1)
        └─ Pod 通过 annotation scheduling.k8s.io/group-name 归属 PodGroup

Volcano Job 只是「便捷控制器」：它把多 Task 模板展开成 Pod、写好 minAvailable/minSuccess/policies，并创建 PodGroup（job_controller_actions.go#L825-L880）。裸 Pod 只要带 group-name 注解且 schedulerName: volcano，PodGroup 控制器也会为它补建 PodGroup（pg_controller_handler.go#L293-L319）。

2.1 Job 字段落到 PodGroup

Job 的调度相关字段基本 1:1 写进 PodGroup，但两者不是同一层对象：

Volcano JobPodGroup语义
spec.minAvailablespec.minMembergang 门槛：本 Job 至少要同时可调度的成员数；也是 phase 判定的阈值
spec.tasks[].minAvailable / partitionPolicyspec.minTaskMember每个 task 角色的最小数，gang 用它做「每角色都要够数」的检查
spec.queuespec.queue指向 cluster-scoped Queue；不存在则不会被调度
spec.priorityClassNamespec.priorityClassName最终被 cache 解析成 JobInfo.Priority，供 priority 插件排序/选 victim
spec.networkTopologyspec.networkTopologyhard/soft + 最高拓扑层，供 hyperNode 搜索
—spec.minResources准入预留：enqueue 时按它判断队列/集群放不放；不是实际分配量
—spec.subGroupPolicy子组级 gang 与拓扑域，是 minTaskMember 的演进方向

字段定义见 scheduling/v1beta1/types.go#L174-L230，Job 侧见 batch/v1alpha1/job.go#L55-L127。

两个「门槛」别混：minMember 是调度门槛（不到就不 bind，见 §5），minResources 是准入门槛（enqueue 时读，见 §4）。前者决定 gang 原子性，后者决定队列配额预留。

2.2 Queue：weight / capability / guarantee / deserved 各管一段

Queue 是集群级对象，字段语义经常被混为一谈（types.go#L622-L681）：

字段作用谁读它
weight相对权重，用于按 weight/totalWeight × totalResource 切分proportion 插件；capacity 不读
capability队列资源上限（硬顶）capacity/proportion 的 realCapability/deserved 计算
guarantee.resource给本队列预留、其他队列不能动的资源capacity（proportion 也用它做 deserved 下限）
deserved显式的「应得份额」，超出部分可被回收仅 capacity 插件；官方文档明确写 “only used by capacity plugin”
reclaimable是否允许别的队列回收本队列资源，默认 true（queue_info.go#L173-L187）reclaim action 的 victim 队列过滤
parent层级队列的父队列capacity/proportion 的层级模式
priority队列排序优先级（高者先、回收时后动）QueueOrderFn
dequeueStrategy声明 fifo（严格队头）/ traverse（跳过卡住的队头）；v1.16.1 核心仓库只把它映射到 NamespaceQueue，scheduler 侧没有消费点（grep 仅命中 API 类型与转换），不要依赖它控制出队暂无

三者关系有明确约束：guarantee ≤ deserved ≤ capability，且 deserved 必须显式配置、capability 子队列不能超过父队列（见队列资源管理）。 注意 capability 是上限、guarantee 是下限、deserved 是「可被回收的界线」——它们不是同一个配额概念的三种写法。

Queue 的 status.allocated 由调度器在 CloseSession 时按 Session 内任务重算并写回（含父队列累加，session.go#L483-L513），所以它天然滞后于真实 Pod 状态一个调度周期。

2.3 PodGroup phase 以代码为准

phase 常量只有五个（types.go#L39-L59），但取值不是控制器随便写的，而是 CloseSession 时由 getPodGroupPhase 从任务状态重算（session.go#L563-L617）：

// 已调度数 = ScheduledStatus（Running/Bound/Failed/Succeeded）+ 已绑定的 Releasing
scheduled := int(jobInfo.ScheduledTaskNum())
completed := 0
for s, tasks := range jobInfo.TaskStatusIndex {
    if api.CompletedStatus(s) { completed += len(tasks) }
}
scheduled += int(jobInfo.ReleasingScheduledTaskNum())

if int32(scheduled) >= jobInfo.PodGroup.Spec.MinMember {
    if scheduled == completed { return scheduling.PodGroupCompleted }
    return scheduling.PodGroupRunning
}
if jobInfo.PodGroup.Status.Phase != scheduling.PodGroupInqueue {
    return scheduling.PodGroupPending
}
return jobInfo.PodGroup.Status.Phase

三个细节：Completed 有「锁存」逻辑（一旦 Completed 且剩余任务都终态就保持，避免 TTL 删除过程中被降级回 Pending 又被重新 enqueue）；Unknown 只在「有 Running 任务且本 session 打了 Unschedulable condition」时出现；Inqueue 由 enqueue action 推进（未配置 enqueue 时 allocate 会兜底改写），不会被这个函数重算掉。

还要注意 ScheduledStatus 只包含 Running/Bound/Failed/Succeeded，不含 Allocated/Binding：Statement Commit 后任务只是 Binding，要等 informer 看到带 nodeName 的 Pod 才进入 Bound/Running。所以 PodGroup 变 Running 不仅滞后一个 session，还依赖 apiserver/informer 的确认。

stateDiagram-v2
    [*] --> Pending: 控制器创建 PodGroup
    Pending --> Inqueue: enqueue 通过 JobEnqueueable
    Inqueue --> Running: scheduled >= minMember
    Inqueue --> Inqueue: 未达 minMember 时保持
    Running --> Completed: scheduled == completed
    Running --> Unknown: 有 Running 且 Unschedulable=true
    Completed --> Completed: 锁存(剩余任务终态)

三、Session：一次调度回合的快照与插件运行时

vc-scheduler 每 --schedule-period（默认 1s，options.go#L36-L48）执行一次 runOnce：开 Session → 跑 Action → 关 Session（scheduler.go#L138-L165）。

OpenSession 做的事（framework.go#L59-L90）：

  1. cache.OnSessionOpen()，然后 snapshot := cache.Snapshot()：深拷贝 Jobs、Nodes、Queues、NamespaceInfo、HyperNodes（session.go#L258-L270）。
  2. 记录 PodGroupOldState（status + annotations），用于 Close 时判断要不要写 API。
  3. 建虚拟顶层 HyperNode、按 tier 整理拓扑；把所有 Node 的 Allocatable 累加成 Session.TotalResource（session.go#L303-L318）。
  4. 按 tiers 配置顺序实例化插件并调用 OnSessionOpen(ssn)：插件在这个回调里注册回调函数、计算本 session 的队列/作业视图（如 capacity 的 per-queue deserved）。
  5. InitCycleState()：为每个 Pending 且未被 gate 的任务建一份 CycleState，供 PrePredicate/Predicate 之间传状态。
  6. applyCachedSkips()：把 unschedulable-job cache 的结论套到本 session（被抑制的 Job 不再尝试）。

Session 是内存视图，action 里所有的分配、驱逐、pipeline 都只改这份克隆；真正写 API 的只有三处：Statement 的 Commit（bind/evict）、Session 关闭时的状态回写、以及 shuffle 直接调 ssn.Evict。这也是为什么「调度成功」必须拆成「内存分配」「bind 请求」「Pod 真正 Running」三段来看。

CloseSession 的顺序（framework.go#L92-L101、session.go#L540-L561）：

  1. 每个插件 OnSessionClose——gang 在这里写 Unschedulable/Scheduled condition。
  2. JobUpdater.UpdateAll() 并发逐 Job 调 updateJob：重算 phase、同步 hyperNode 注解，只有状态/注解变了或 Job 被标 dirty 才 cache.UpdateJobStatus（job_updater.go#L136-L150）。
  3. updateQueueStatus：按 Session 内任务的 AllocatedStatus 重算每个队列（含祖先）的 allocated 并写回。
  4. reconcileUnschedulableCache、cache.OnSessionClose，然后把 Session 字段置 nil。

3.1 Session 内状态 vs cache

维度SessionSchedulerCache
生命周期一次 runOnce（默认 1s）进程级，随 informer 持续更新
数据来源Snapshot() 深拷贝informer 事件（Pod/Node/PodGroup/Queue）
资源账本NodeInfo.Idle/Used/Releasing 的克隆，Action 内随便改真实 NodeInfo；AddBindTask/Evict 会立刻改它
任务状态Action 改的是克隆的 TaskStatusIndex只有 bind/evict 相关的状态变更会进 cache

DirtyJobs 容易被误解：它不是「所有被改过的 Job」，而是需要在 Close 时把 hyperNode 提名/placement 写回 cache 的 Job（allocate 的 nominated 分支会 MarkJobDirty）。普通的任务分配状态不需要这个标记，因为 PodGroup status 本来就会被重算。

四、Action 管线：默认三个，扩容必须显式配置

默认 scheduler conf 只有三个 action（util.go#L38-L51）：

actions: "enqueue, allocate, backfill"
tiers:
- plugins:
  - name: priority
  - name: gang
  - name: conformance
- plugins:
  - name: overcommit
  - name: drf
  - name: predicates
  - name: proportion
  - name: nodeorder
Action做什么默认关键前提
enqueuePending → Inqueue；按 JobEnqueueable（overcommit/capacity/proportion）与 Queue 状态做准入✅Job 无 minResources 时直接放行
allocate队列→Job→Task 三级选择，predicate + node order，gang 达标才 commit✅需 Job 已不是 Pending（否则跳过）
backfill只给「无资源请求、无 DRA claim」的 BestEffort 任务找节点✅不做 gang/配额校验
preempt队列内、按优先级抢占，让 starving job 变 pipelined❌ 显式配置必须有 Pending 任务
reclaim跨队列按权益回收（overused/preemptive/reclaimable）❌同上
gangpreempt以整 Job/bundle 为单位驱逐，按 HyperNode 域做提名❌新增 action（文件头 Copyright 2026），参数 maxDomains/allowWholeBundle
gangreclaim同上，但跨队列回收❌同上
shuffle按插件的 VictimTasksFn 选一批 Running 任务直接驱逐❌只驱逐、不分配

顺序不是随意的，至少四条理由：

  1. enqueue 必须在 allocate 之前：allocate 只处理非 Pending 的 Job。若配置里没有 enqueue，allocate 会把 Pending 在内存里改成 Inqueue 再继续（allocate.go#L173-L186），但这只是兜底。
  2. allocate 必须在 preempt/reclaim 之前：先试便宜路径（有空闲就分配），只有仍然 starving 的 Job 才值得付驱逐成本。反过来会把还能正常调度的 victim 先杀掉。
  3. allocate 必须在 backfill 之前：有资源请求的 Pod 先占位，BestEffort 再用剩下的节点填空；backfill 自己不检查 gang，也不走 Statement。
  4. enqueue 与 preempt/reclaim 存在语义冲突：官方文档明确提示，若 enqueue 判定 Job 不能入队，控制器就不会创建 Pending Pod，后续 preempt/reclaim 也就没有对象可抢（Actions 文档）。生产配置通常二选一，或让 enqueue 足够宽松。

gangpreempt/gangreclaim 与 preempt/reclaim 是两代实现：后者的粒度是 task，前者把「整个 Job 的待调度任务」作为一个 bundle，在最多 maxDomains 个 HyperNode 域里选 victim 组合，成功后把 NominatedHyperNode 写回 SubJob，交给下一个 allocate 周期兑现（gangpreempt.go#L79-L139）。两者不建议同时开启。

五、allocate 与 backfill：gang 分配和 BestEffort 填空

5.1 allocate 的三级选择

allocate.Execute 的注释就是算法骨架：选 Queue → 选 Job → 选 Task → predicate 过滤 → node order 选点（allocate.go#L138-L158）。

  • 队列：PriorityQueue(QueueOrderFn)，按插件给出的顺序取；overused 的队列直接跳过（allocate.go#L356-L372）。
  • Job：JobOrderFn 决定；JobValid 失败、被 unschedulable cache 抑制、队列不存在的 Job 都跳过。
  • Task：TaskOrderFn；每次取一个，先查 ssn.Allocatable(queue, task)——这是队列权益在分配侧的唯一闸门。
  • 节点：PrePredicateFn → 若 Pod 带 status.nominatedNodeName 且该节点仍在候选域内，优先只试它 → 否则对所有节点跑 PredicateNodes（资源 fit + 各插件 predicate）。注意 predicate 返回 Unschedulable/UnschedulableAndUnresolvable/ErrorSkipOrWait 都算失败，其余错误被忽略（session.go#L662-L690）。
  • 打分：候选节点分两档——Idle 够用的（第一档）与只有 FutureIdle（含 Releasing）够用的（第二档）。第一档有解就不看第二档；同档内用 BatchNodeOrderFn/NodeOrderFn 打分，BestNodeFn 或最高分胜出（allocate.go#L1154-L1223）。
  • 落账：第一档节点 → stmt.Allocate（占 Idle）；第二档 → stmt.Pipeline（占 Releasing，任务变 Pipelined，等 victim 真正退出后再 bind）。

5.2 gang 门槛与 statement 的生命周期

allocateResourcesForTasks 会为一个 SubJob 的所有 Pending 任务开一个 Statement，逐个分配；每分配完一个就检查 SubJobReady，达到门槛立即停手，调用方再检查 JobReady 决定是否 Commit（allocate.go#L925-L1000）。如果整轮下来没达到门槛：

  • 任务没达到 SubJobPipelined → stmt.Discard()，内存里的分配全部逆序回滚，等于这个 Job 本轮一个都没占；
  • 达到了 SubJobPipelined 但 Job 没 Ready → 只返回 statement，不 Commit：内存里仍算占位，但不会发 bind，session 结束后自然消失。

这正是 Volcano gang 的实现方式：先在一个 Statement 里试满整组，再决定是否提交。它没有原生 Permit 那样的「等待队列」——等的是下一个调度周期，而不是在 bind 周期里阻塞。

集群级队列闸门来自 Allocatable：proportion 比较 allocated + req ≤ deserved，capacity 则逐层检查 capability/deserved（含祖先）。两者都注册 SimulateAllocatableFn，供抢占时的 dry-run 使用。

5.3 backfill：只补 BestEffort，不保证 gang

backfill 的选择范围比很多人以为的窄（backfill.go#L60-L135、#L137-L200）：

  1. 跳过 Pending 的 Job（未入队的 Job 不该被填进来）。
  2. 只取既没有普通资源请求、也没有 DRA claim 的 Pending 任务——即 BestEffort Pod。有请求的任务留给 allocate。
  3. 对 Pipelined 的同类任务先 stmt.UnPipeline 拉回 Pending，再重新找节点。
  4. 每个任务独立走：PrePredicateFn → 全节点 PredicateNodes → 若只有一个候选就直接用，多候选时仍走 BatchNodeOrderFn 选最优 → ssn.Allocate（不走 Statement 批量）。失败时只把错误写进 NodesFitErrors 并继续下一个任务；因为没有 Statement，也就没有批量回滚，前一个任务已经做的内存改动不会被撤销。

所以 backfill 不检查 JobReady，也不调用 Allocatable：它不保证 gang 原子性，也不做队列配额判断（这些任务的 request 为 0，配额账本本来也记不到它们头上）。它提高利用率的方式很直接：不等整组到齐，先把零请求 Pod 塞进节点空位；但这些 Pod 仍占 Pod 数量槽位、可能改变后续 gang 的 predicate/亲和性结果——而且 JobInfo.IsReady() 会把 Pending 的 BestEffort 任务也计入（job_info.go#L1352-L1362）；不过 gang 的 JobReady 还要求 CheckTaskReady，所以这主要影响 gang 的 JobOrderFn 排序，不一定能让 gang 门槛通过。

六、preempt 与 reclaim：只处理 starving / overused

两者共享同一套骨架（挑 starving Job → 逐 task → 在节点上选 victim → 用 Statement 试 → 成功才 Commit），差别在范围和判定依据。

6.1 preempt：队列内按优先级

  1. 预选 preemptor Job：非 Pending、JobValid 通过、JobStarving(job) 为真、且不含 networkTopology（当前版本明确跳过带拓扑的 Job，preempt.go#L101-L158）。
  2. 两层循环：队列内 Job 之间（victim 必须同队列、不同 Job）与 Job 内 Task 之间（victim 必须同 Job）。
  3. 每个 preemptor task：PreemptionPolicy: Never 直接拒；PrePredicateFn；带 nominatedNodeName 时若该节点上有「已被抢占、正在终止」的低优 Pod 则本轮不再抢（防重复驱逐）。
  4. 排除 allocate 阶段已标记 UnschedulableAndUnresolvable 的节点，再跑 PredicateForPreemptAction（只把不可解/跳过类错误当失败，可解的资源不足留给抢占解决）。
  5. 逐个节点：把 Running、Preemptable、同队列的 victim 交给 ssn.Preemptable 做 tier 交集；ValidateVictims 确认资源确实够；按最低优先级先驱逐，直到 preemptorFitsOnNode（Allocatable + 资源 + predicate）为真；然后 Pipeline preemptor。每个节点用独立 nodeStmt，失败就 Discard，成功才 Merge 进主 statement（preempt.go#L340-L390）。
  6. 循环结束后只有 JobPipelined(job) 为真才 Commit：commit 才真正调 cache.Evict 删 victim Pod；否则 Discard 把内存里的驱逐逆序撤销。

victim 的合法性由插件交集决定：gang 保证 victim Job 剩余数不低于 MinAvailable，priority 保证优先级更低，pdb 保证 disruptionsAllowed 不被击穿，conformance 保证 kube-system 与 critical Pod 不被选。SelectVictimsOnNode 还做了「取出最小 victim 集合后再逐个放回」的 reprieve 逻辑（preempt.go#L739-L800），避免一次杀太多。

6.2 reclaim：跨队列按权益

reclaim 的入口判定换了（reclaim.go#L57-L88、#L180-L264）：

  • 队列维度：Overused(queue) 为真则整队跳过；每个 task 还要过 Preemptive(queue, tasks)——proportion 用它判断「加上这些请求后是否仍在 deserved 内」，capacity 用它判断 realCapability 与逐维 deserved（含祖先）。
  • victim 维度：只选其他队列的 Running/Preemptable 任务，且那个队列 spec.reclaimable 不为 false；再交给 ssn.Reclaimable 做 tier 交集（gang 保护 minAvailable、capacity 保护 guarantee/deserved、proportion 保护 deserved、pdb 过滤）。
  • 满足条件同样是「驱逐到 reclaimerFitsOnNode 成立 → Pipeline → Merge」，最后 JobPipelined 才 Commit。

一个关键实现事实：默认配置里只有 proportion 注册 OverusedFn（另有可选的 extender 插件也会注册）。纯 capacity 配置下 ssn.Overused() 恒为 false，队列不会被这一步短路，真正的约束由 Preemptive/Reclaimable 里的 deserved/guarantee 比较承担。这也是为什么官方 capacity 指南要求「启用 capacity 时同时启用 reclaim」。

七、插件：注册了哪些回调，改变哪个决策

插件不是 Framework 插件，而是在 OnSessionOpen 里往 Session 注册回调函数。Session 按 tiers 顺序遍历插件调用这些回调，语义分三类（session_plugins.go#L491-L569、#L702-L860）：

  • AND 式（JobReady、Allocatable、JobValid、SubJobReady）：任一插件返回 false 即失败。
  • 首个结论式（Preemptable/Reclaimable/JobPipelined/JobStarving/JobEnqueueable）：同一 tier 内取交集或投票，某一 tier 一旦给出结论就返回，不再看下一 tier。
  • 排序式（JobOrderFn/TaskOrderFn/QueueOrderFn）：按 tier 顺序取第一个非零比较结果，不是加权求和；全为 0 时用创建时间/UID 等兜底。

每个插件还可以按回调粒度开关（enableJobOrder、enabledPreemptive 等），默认全开（scheduler_conf.go#L26-L44）。

几点值得单独说：

  • gang 的 victim 保护是「preemptee 所属 Job 的 Ready 数 > minAvailable 才可杀」，按 Job 逐个扣减模拟（gang.go#L101-L160）。它是「不把别人打到 gang 以下」，不是「victim 也得是 gang 成员」。
  • capacity 的 realCapability 不是简单的 capability：它是 ExceededPart(totalResource, totalGuarantee) + guarantee，再被 capability 逐维截断（capacity.go#L1077-L1099）。所以 capability 配得比「集群减预留」还大时也不会真的超卖。
  • proportion 的 overused 定义是 deserved ≤ allocated（proportion.go#L326-L339），share 取各资源维度 allocated/deserved 的最大值；排序先看队列 priority，再看 share。
  • capacity vs proportion：capacity 用显式 deserved 做「借出/回收」的界线，支持层级与祖先回收；proportion 用 weight 动态算 deserved，是扁平权重模型。两者冲突，不能同时启用（capacity 用户指南）。
  • network-topology-aware 的 hard 模式会按 highestTierAllowed 收紧搜索域，soft 模式只在已分配域为空时退化为不约束（network_topology_aware.go#L271-L315）。
  • predicates 里的 DRA：它直接实例化上游 dynamicresources 插件并挂到 PreFilter/Filter/Reserve/PreBind/Score（predicates.go#L611-L623）。所以 Volcano 的 Statement 不覆盖 claim 分配，claim 的分配与回滚走的是上游插件的 PreBind/PreBindRollBack，capacity 另外按 DeviceClass 记 DRA 配额。

八、Statement 事务：Commit/Discard 与原生 assume 的差异

Statement 是 Volcano 自己的「事务层」，只有三种操作：Evict、Pipeline、Allocate（statement.go#L38-L57）。它的工作方式是「内存先改，操作记账，最后统一提交或逆序撤销」：

  • Allocate(task, node)：立刻改 session 克隆（任务 → Allocated、node.AddTask 扣 Idle），记一条 Allocate 操作；回调出错则当场 unallocate 回滚（statement.go#L258-L327）。
  • Pipeline(task, node)：任务 → Pipelined、占 Releasing，记 Pipeline；失败当场 unPipeline。
  • Evict(victim)：任务 → Releasing、node.UpdateTask，记 Evict。
  • Discard()：倒序遍历操作，依次 unevict/unPipeline/unallocate（statement.go#L377-L401）。
  • Commit()：正序遍历，Evict → cache.Evict（真删 Pod），Allocate → cache.AddBindTask（入 bind 队列）；Allocate 失败会 unallocate，Evict 失败会 unevict（statement.go#L404-L428）。

还有两个进阶用法：Merge 把多个子 statement 的操作合并（preempt/reclaim 里每个节点一个子 statement，成功才并入主 statement）；SaveOperations + RecoverOperations 用于 dry-run——allocate 在多个 HyperNode 候选上试算，留下最优的那个再「重放」操作。

和原生 assume 的区别，最少有这五点：

最容易被误读的一点：Statement 的 Allocate 并不等于 assume。原生 assume 之后 Pod 已经在 cache 里「占位」，绑定失败要靠 ForgetPod 撤回；Volcano 的 Allocate 只在 Session 里占位，真正进入 cache 是 Commit → AddBindTask（cache.go#L1485-L1524），而那已经是 bind 请求入队，不是「假设」。

不能直接替换名称，举四个最常见的错位：

  1. 「Volcano 的 predicate = 原生 Filter」不成立：原生 Filter 是框架扩展点，返回 status 后由 runtime 决定后继（unschedulable/抢占）；Volcano 的 PredicateFn 是 action 内部调用的函数，返回值还要经过 PredicateForAllocateAction/PredicateForPreemptAction 两种不同过滤，调用者、状态、失败语义都不同。
  2. 「gang 插件 = Permit」不成立：Permit 是异步等待 + 超时；Volcano 的 gang 是同一次 session 内的「试满再提交」，没有等待队列。
  3. 「Queue = Kueue ClusterQueue」不成立：Volcano Queue 直接参与每一轮 allocate/reclaim，Kueue ClusterQueue 只决定准入。
  4. 「deserved = nominalQuota」不成立：deserved 是「可被回收的界线」，nominalQuota 是准入的名义配额；公式与生效点都不同。

十、正确性边界：窗口在哪里

Volcano 的一致性依赖「Snapshot 克隆 + Statement 试算 + informer 校正」，因此有几个必须知道的窗口：

失败/边界发生位置处理后果
predicate 全失败allocate/backfill写 NodesFitErrors，不 bindJob 可能本轮不 Ready，phase 保持
Statement 内回调失败Allocate/Pipeline当场 unallocate/unPipeline单个 task 回滚，其余继续试
AddBindTask 失败Commitunallocate + 记日志该任务回 Pending（session 内）
apiserver Bind 失败异步 cache.BindPreBindRollBack、写 PodScheduled=False、resyncTaskSession 已关，靠 informer 重新对齐
cache.Evict 失败Commitunevict 回滚内存victim 仍在，preemptor 下轮再试
PreBind 失败bind 前逆序回滚已执行的 PreBinderclaim/volume 分配不会遗留
PodGroup status 写失败CloseSession打日志下个周期用旧状态重算；状态由任务推导，通常能自愈

两个实践上最重要的窗口：

  • bind 是异步批处理的：processBindTask 每 20ms 轮询一次队列，攒够 batchNum 就交 BindTask 起 goroutine 发 Bind（cache.go#L1603-L1622）。所以「Action commit 完」不等于「Pod 已绑定」，下一个 session 的 Snapshot 可能还没看到这些 bind。
  • preempt 后 victim 只是被删：Pod 有优雅终止期，资源不会立刻回来；preemptor 停在 Pipelined，直到后续 session 看到资源释放才转 Allocated。这段时间里，nominatedNodeName 与「terminating by preemption」检查是防止反复抢占的唯一护栏。

Volcano 的恢复模型很朴素：Session 里没有持久状态，Statement 未 Commit 就没有 API 副作用；重启后 cache 从 informer 全量重建，已绑定的 Pod 靠 spec.nodeName 直接恢复，未绑定的重新走 enqueue/allocate。换句话说，它把一致性责任推给了 Kubernetes 的对象状态，而不是自己的 WAL。
