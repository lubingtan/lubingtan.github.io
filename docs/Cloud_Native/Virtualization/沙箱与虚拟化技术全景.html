沙箱与虚拟化技术全景：KVM、QEMU、Firecracker、Kata、gVisor

这五个词经常被并列提起，但它们不在同一个层次上：KVM 是内核里的虚拟化接口，QEMU 和 Firecracker 是用户态的 VMM，Kata 是容器运行时，gVisor 是用户态内核。把这五个东西排成“从硬件到容器“的一条线，很多混淆会自然消失。

本文的重点不是复述官方文档，而是回答四个问题：

  1. 每个东西到底负责哪一层，它的隔离边界落在 CPU 的哪一级特权上；
  2. 它们之间谁调用谁，哪些是替代关系、哪些是组合关系；
  3. “容器 / 沙箱 / 虚拟机“三个词在什么语境下才是同义的；
  4. 面对一个具体需求（AI Agent 执行不可信代码、多租户、serverless、GPU 负载）该怎么选。

三条最容易记错的关系：

  • QEMU ≠ KVM：KVM 是内核能力，QEMU 是用户态 VMM；QEMU 可以不用 KVM（TCG 纯模拟），KVM 也可以不用 QEMU（Firecracker/Cloud Hypervisor）。
  • Kata ≠ hypervisor：Kata 是“组装层“，它自己不做 CPU 虚拟化，也不实现 VMM；VMM（QEMU/CH/Firecracker/Dragonball）是可替换组件。
  • gVisor ≠ 虚拟机：默认平台（systrap）不创建 VM、不需要 /dev/kvm；它是用进程 + seccomp 实现的一个“假内核“。

0.3 VMM 是什么：一台虚拟机的“用户态操作系统“

VMM（Virtual Machine Monitor）是负责创建、启动并运行一台虚拟机的软件层。 在 KVM 体系里这句话有更具体的含义：KVM 只在内核提供 CPU/内存虚拟化的原语，把“能启动、有设备、能管理“的一台 VM 拼出来的是 userspace 的 VMM。

VMM 的四件事（这四件缺一不可，也是判断“某东西是不是 VMM“的标准）：

职责做什么代码里的落点
1. 管 vCPU为每个 guest CPU 创建 KVM vCPU，起宿主线程跑 KVM_RUN 循环，处理每次 VM exitFirecracker vcpu.rs#L407-L432；QEMU kvm-all.c#L3445-L3482
2. 管内存分配/映射 guest RAM，告诉 KVM“这段 gpa 对应我进程里的哪个 hva“（memslot）KVM_SET_USER_MEMORY_REGION 的 5 字段结构（kvm.h#L29-L36）；Firecracker vm.rs#L453-L475；QEMU kvm-all.c#L380-L411
3. 造虚拟平台设备模型（virtio/legacy/PCI）、中断、固件/ACPI；把 IO/MMIO exit 翻译成设备读写QEMU hw/virtio/virtio.c#L3766；Firecracker 设备 attach 顺序 builder.rs#L242-L303；exit 分发 vmx.c#L6329-L6389
4. 管生命周期加载内核/固件、启动/暂停/恢复、快照、迁移、对外的管理 APIFirecracker 用 linux-loader 直接引导（arch/x86_64/mod.rs#L495-L548）、快照 persist.rs#L169-L198）；QEMU 加载 bios.bin（pc_sysfw.c#L247-L254）

把上面四件事写成伪代码，VMM 的主循环其实就是“创建 + 一个 KVM_RUN 循环“：

int kvm  = open("/dev/kvm", O_RDWR);
int vm   = ioctl(kvm, KVM_CREATE_VM);
void *ram = mmap(...);                                  /* guest RAM 由 VMM 分配 */
ioctl(vm, KVM_SET_USER_MEMORY_REGION, &(struct kvm_userspace_memory_region){
    .slot = 0, .guest_phys_addr = 0, .memory_size = RAM_SIZE, .userspace_addr = ram });
int vcpu = ioctl(vm, KVM_CREATE_VCPU, 0);
struct kvm_run *run = mmap(vcpu_run_fd, KVM_GET_VCPU_MMAP_SIZE);
for (;;) {
    ioctl(vcpu, KVM_RUN);            /* 进入 guest；返回 = 一次 VM exit */
    switch (run->exit_reason) {
    case KVM_EXIT_IO:   /* 设备模型应答 */ break;
    case KVM_EXIT_MMIO: /* 设备模型应答 */ break;
    case KVM_EXIT_HLT:  /* guest 停机 */   break;
    }
}

伪代码省略了 vCPU 寄存器初始化、多 vCPU 线程、kvm_run 映射大小、信号/暂停处理等；真实实现见 Firecracker builder.rs#L165-L205 与 QEMU accel/kvm。

VMM 与相邻概念的边界（这是“VMM 是什么“最容易被问混的部分）：

概念是什么不是什么
VMM创建/运行 VM 的 userspace 程序：QEMU、Firecracker、Cloud Hypervisor、crosvm、Dragonball不是内核模块，不是 ioctl API
Hypervisor虚拟化层的统称：bare-metal 的 Xen/Hyper-V，或内核内的 KVM不一定是某个 userspace 程序；KVM 常被叫 hypervisor，但它本身不是产品
AcceleratorQEMU 对“CPU 执行后端“的命名（KVM/TCG/Xen/HVF…）不是 VM，也不是完整的 VMM
Runtime容器生命周期接口的实现（runc/runsc/kata）不直接创建 VM（Kata 内部再调 VMM）
KVM内核里提供 CPU/内存虚拟化原语的接口（/dev/kvm）不是 VMM；不提供设备模型、固件、磁盘/网络后端

一句话记住：KVM 提供“虚拟化原语“，VMM 把原语组装成“一台机器“，runtime 把这台机器（或进程/用户态内核）包装成“容器“。 这也解释了为什么同一套 KVM 能长出 QEMU（全功能）、Firecracker（极简）两种形态完全不同的 VMM——差异全在 VMM 这一层。

1. 为什么这些词总被混在一起

1.1 三个被混用的词：沙箱、虚拟化、运行时

词真正含义回答的问题例子
沙箱（sandbox）一种隔离效果的统称“这段不可信代码最多能碰到什么？”gVisor、Kata、Firecracker、seccomp、Wasm
虚拟化（virtualization）一种实现手段：用硬件/软件造出虚拟的 CPU、内存、设备“怎么造出一台假机器？”KVM、QEMU、Firecracker
运行时（runtime）一种接口/生命周期实现“怎么创建/启动/停止一个容器？”runc、runsc、kata-runtime、containerd

所以「gVisor 是沙箱但不是虚拟机」「Kata 是运行时同时是沙箱」「Firecracker 是 VMM 也是沙箱的底座」这些说法都不矛盾——它们分别在回答不同的问题。

1.2 一条历史线：需求是怎么逼出这些技术的

  1. 2003：QEMU 诞生。用纯软件（TCG 动态翻译）模拟一整台机器，能跨架构跑 OS。它证明“VMM + 设备模型“可以完全跑在用户态（QEMU 官方介绍）。
  2. 2007：KVM 进入 Linux 2.6.20。把 Intel VT-x / AMD-V 包装成 /dev/kvm 的内核 API，QEMU 立刻成为它的用户态搭档——“QEMU/KVM” 组合从此成为 Linux 虚拟化的默认答案（KVM OLS 2007 论文）。
  3. 2013：Docker 引爆容器。namespace + cgroup + 镜像分层让“打包和启动“变得极轻，但隔离边界是共享的宿主内核：容器逃逸 = 内核提权。
  4. 2015–2018：两条强隔离路线出现：
    • 硬件虚拟化路线：Intel Clear Containers（2015）与 Hyper runV 合并为 Kata Containers（2017 年底宣布），思路是“每个 Pod 一个轻量 VM“，兼容 OCI/CRI（Kata 官网）；
    • 用户态内核路线：Google 开源 gVisor（2018），思路是“在用户态重新实现一个 Linux 内核“，把不可信进程的 syscall 全部拦截在 Sentry 里（gVisor 开源公告）。
  5. 2018：AWS 开源 Firecracker。把 VMM 裁到只剩 virtio-net/block/vsock + serial，启动时间压到百毫秒级、内存开销压到 MiB 级，用来支撑 Lambda/Fargate 的高密度多租户。2020 年的 NSDI 论文系统总结了这套设计（NSDI’20）。
  6. 2018–2020：Kubernetes 把“选运行时“标准化。RuntimeClass（1.20 GA）让用户用 runtimeClassName 选择 handler，把 runc / runsc / kata 统一到同一个 Pod API 下（RuntimeClass 文档；链路细节见 容器运行时全链路）。
  7. 2019–至今：组合而不是替代。Kata 支持 QEMU/Cloud Hypervisor/Firecracker/Dragonball 多个 VMM；Confidential Containers（CoCo）把 Kata + 硬件可信执行环境（TDX/SEV-SNP）组合起来；AI Agent 沙箱（如 Agent Sandbox、Agent Substrate）同时使用 gVisor 和 Kata microVM。

说明：上述年份是业界通说；内联链接主要支撑“项目/概念确实存在“，并非逐条考据历史（例如 RuntimeClass 的 GA 版本请以 Kubernetes release note 为准）。

一句话：容器解决了“打包和密度“，虚拟化解决了“隔离边界“，gVisor 提供了第三条路（用户态内核）。三者不是代际替代，而是按“隔离强度 / 兼容性 / 开销“三角做取舍。

1.3 一条判据：隔离边界落在哪个特权级

判断一个技术“强不强“，不要看它叫不叫 sandbox，而要看不可信代码的 syscall 最终由谁处理：

  • 由宿主内核处理 → 共享内核（runc），隔离 = namespace/cgroup/seccomp/LSM；
  • 由用户态内核处理 → 用户态内核（gVisor），隔离 = Sentry 的 syscall 实现 + 宿主 seccomp；
  • 由guest 内核处理，宿主只看到 VM exit → 硬件虚拟化（Kata/Firecracker/QEMU），隔离 = CPU 特权级 + EPT。

这个判据贯穿全文。

3. KVM：把 CPU 虚拟化能力变成 /dev/kvm

本节把 KVM 的概念逐层拆开；读完 §3.1–§3.6 后，可以直接跳到 §3.7 动手实验，用约 150 行 C 把这些概念亲手跑一遍。

3.1 它是什么：内核子系统 + 一套 ioctl ABI

KVM（Kernel-based Virtual Machine）是 Linux 内核里的虚拟化子系统，构建产物是 kvm.ko + 厂商模块 kvm-intel.ko/kvm-amd.ko（arch/x86/kvm/Makefile#L35-L37）。它对外只暴露一个字符设备 /dev/kvm（misc 设备，virt/kvm/kvm_main.c#L5593-L5597），所有能力都通过这个 fd 上的 ioctl 协商。

官方 API 文档开篇就把它定义为“一组发往不同文件描述符的 ioctl“（Documentation/virt/kvm/api.rst#L10-L22），并且这个 ABI 自 Linux 2.6.22 起冻结，只允许向后兼容扩展（api.rst#L90-L98）。版本号 KVM_API_VERSION 固定为 12（include/uapi/linux/kvm.h#L22），userspace 发现返回的不是 12 就应拒绝运行。

这句话是理解 KVM 的关键：KVM 本身不创建“一台虚拟机“，它只提供让 userspace 能创建虚拟机的基础设施。

Type-1 / Type-2 的归类：业界对 KVM 的归类并不一致——它既不是 Xen/Hyper-V 那种直接跑在裸机上的 hypervisor，也不是用户态 VMM，而是宿主 Linux 内核里的模块；配上 QEMU/Firecracker 等 userspace VMM 后才构成完整方案。Kata 文档把 QEMU/KVM 归为 “Type 2”（virtualization.md#L97-L108）。讨论时说明口径即可，不必纠结标签。

CPU、内存、设备、固件都要由 userspace 一样样“喂“进去——这就是 VMM 的职责。

3.3 guest 内存：memslot 只是把 gpa 指向 VMM 的用户内存

KVM 不分配 guest 内存。它只接受一个 5 字段的契约（kvm.h#L29-L36）：

struct kvm_userspace_memory_region {
    __u32 slot;            /* slot id（低 16 位）+ address space id（高 16 位） */
    __u32 flags;           /* read-only / dirty log 等 */
    __u64 guest_phys_addr; /* guest 物理地址(gpa) */
    __u64 memory_size;
    __u64 userspace_addr;  /* VMM 进程里的用户地址(hva) */
};

内核把它换算成 base_gfn/npages 并保存 userspace_addr（kvm_main.c#L2070-L2071、#L2108-L2113）；slot 低 16 位是 slot id、高 16 位是 address space id（多地址空间时），见 api.rst#L1390-L1401。所以 gpa → hva 的翻译完全由 userspace 定义：

“Guest memory (gpa) is part of the user address space of the process that is using kvm. Userspace defines the translation between guest addresses and user addresses (gpa->hva).”（Documentation/virt/kvm/x86/mmu.rst#L92-L95）

这也解释了两件事：为什么 KVM 能配合 mmap/userfaultfd 做内存快照和按需加载；以及为什么“host 内核能访问 guest 内存“——物理上它就是 VMM 进程的匿名页。

3.4 执行：KVM_RUN 进、VM exit 出

KVM_RUN 是“进入 guest“的唯一入口，返回即代表发生了一次 VM exit（或出错/被信号打断）。x86 调用链：

  1. kvm_vcpu_ioctl() 的 case KVM_RUN → kvm_arch_vcpu_ioctl_run()（kvm_main.c#L4469-L4509）；
  2. kvm_arch_vcpu_ioctl_run() → vcpu_run()（arch/x86/kvm/x86.c#L8885、#L8990）；
  3. vcpu_run() 是 for (;;) 循环：可运行就 vcpu_enter_guest()，否则 vcpu_block() 等事件（x86.c#L8635-L8656）；
  4. 真正进入 guest 的是厂商 op：exit_fastpath = kvm_x86_call(vcpu_run)(vcpu, run_flags)（x86.c#L8371）；
  5. 从 guest 返回后统一走 handle_exit（x86.c#L8495）；Intel 上是函数表 kvm_vmx_exit_handlers[]（vmx.c#L6329-L6389）。

userspace 与内核共享的参数块是 mmap vcpu fd 得到的 struct kvm_run（kvm.h#L223-L244），exit_reason 及 io/mmio 联合体由内核写、userspace 读。x86 上这块区域通常是 3 页（kvm_run + pio data + coalesced MMIO ring，kvm_main.c#L5569-L5579）。

三种最常见的 exit：

Exit 原因触发场景KVM 内处理最终去向
EPT_VIOLATIONguest 访问的 gpa 在 EPT 里没有翻译/权限不足（缺页、写保护、MMIO 区）handle_ept_violation() → kvm_mmu_page_fault()（vmx.c#L5972-L6003）通常内核内补映射；无 memslot 覆盖时升级为 KVM_EXIT_MMIO

注意：KVM_EXIT_IO/KVM_EXIT_MMIO 这类操作要等 userspace 再次 KVM_RUN 才算完成（api.rst#L6838-L6852）。GPU、网卡、磁盘的性能在很大程度上就取决于这条“exit → userspace → 再进 guest“的往返。

3.5 硬件虚拟化：VMX/SVM、VMCS、EPT/NPT

  • VMX root / non-root：Intel 上用 VMX 运行 guest，guest 在 VMX non-root operation 下直接以硬件速度执行；guest 里的 ring 0 并不是真实最高特权级。
  • VMCS：保存 guest/host 状态与 exit 控制的控制结构。KVM 把 host 恢复点写进 HOST_RIP（vmx.c#L4495），所以 vmlaunch/vmresume 之后控制流会“魔法般“在 vmx_vmexit 处恢复（vmenter.S#L89-L114）。
  • EPT（stage-2 地址翻译）：guest 页表负责 gva→gpa（stage-1），EPT 负责 gpa→hpa（stage-2）。KVM 把 EPT 根页表物理地址构造成 EPTP 写进 VMCS（vmx.c#L3333-L3354）。这就是“两维分页“（Documentation/virt/kvm/x86/mmu.rst#L62-L67）。
  • AMD 对应 SVM + NPT：vmrun 指令进入 guest，控制结构是 VMCB，NPT 默认开启（svm.c#L135-L140、svm/vmenter.S#L100-L107）。
  • “KVM 只在 exit 时回到 host 内核“的准确含义：guest 运行期间，该 vCPU 线程在 host 内核里没有执行任何代码；CPU 处于 non-root/guest 模式。发生 VM exit 后，同一个线程、同一个进程才在内核上下文里跑 KVM 的 exit 处理。KVM 确实有指令模拟器（arch/x86/kvm/emulate.c），但那是处理 MMIO/PIO/特权指令的补充路径，不是执行 guest 的主方式。

3.6 能力边界：KVM 提供什么、不提供什么

所以选型时不要把 KVM 当作一个产品：没有 QEMU/Firecracker/Cloud Hypervisor 这些 VMM，KVM 自己连一台能启动的虚拟机都拼不出来。

3.7 动手实验：用约 150 行 C 亲手跑一个最小 VMM

实验目标：把 §3.1–§3.4 从“读代码“变成“亲眼看到“——亲手打开 /dev/kvm、创建 VM 和 vCPU、登记一段 guest 内存，然后看着 guest 的 out / hlt 指令变成 KVM_EXIT_IO / KVM_EXIT_HLT。

实验 guest 是 5 字节的 16 位实模式程序：mov al,'A'; out 0xe9,al; hlt。VMM 把 out 的数据打印出来，然后看到 hlt 结束。完整代码已作为附件放在页面目录：tiny-kvm.c。

Step 1：代码

/*
 * tiny-kvm.c — 用最小代码亲手跑一个 KVM 虚拟机（16 位实模式）
 *
 * 学习目标：直接观察 KVM 的三类 fd 与 KVM_RUN/VM exit 模型：
 *   1) /dev/kvm  --KVM_CREATE_VM-->        VM fd
 *   2) VM fd     --KVM_SET_USER_MEMORY_REGION--> 一段 gpa 指向本进程的用户内存
 *   3) VM fd     --KVM_CREATE_VCPU-->      vCPU fd
 *   4) vCPU fd   --KVM_RUN-->             进入 guest；返回即一次 VM exit
 *
 * guest 代码（放在 gpa 0，16 位实模式）：
 *   B0 41        mov al, 0x41        ; 'A'
 *   E6 E9        out 0xe9, al        ; 0xe9 是未分配的调试端口 -> KVM_EXIT_IO
 *   F4           hlt                 ; -> KVM_EXIT_HLT
 *
 * 编译: gcc -O2 -Wall -Wextra -o tiny-kvm tiny-kvm.c
 * 运行: ./tiny-kvm   (需要 /dev/kvm 且当前用户可读写)
 */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <linux/kvm.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/ioctl.h>
#include <sys/mman.h>
#include <unistd.h>

#define RAM_SIZE   0x1000ULL          /* 1 页 guest 物理内存 */
#define TSS_ADDR   0xfffbd000ULL      /* Intel VMX 需要的 TSS 区域（不映射也不访问） */

static void die(const char *what)
{
    fprintf(stderr, "%s: %s\n", what, strerror(errno));
    exit(1);
}

int main(void)
{
    int kvm = open("/dev/kvm", O_RDWR | O_CLOEXEC);
    if (kvm < 0) {
        fprintf(stderr, "open /dev/kvm: %s\n", strerror(errno));
        fprintf(stderr, "提示: 确认内核加载了 kvm 模块、/dev/kvm 存在，且当前用户在 kvm 组（或对该设备有 rw 权限）。\n");
        return 1;
    }

    int api = ioctl(kvm, KVM_GET_API_VERSION, 0);
    if (api < 0)
        die("KVM_GET_API_VERSION");
    if (api != KVM_API_VERSION) {
        fprintf(stderr, "unexpected KVM API version %d (expected %d)\n", api, KVM_API_VERSION);
        return 1;
    }
    printf("KVM API version: %d\n", api);

    int vm = ioctl(kvm, KVM_CREATE_VM, 0);
    if (vm < 0)
        die("KVM_CREATE_VM");

    /* Intel VMX 上必须在创建 vCPU 前设置 TSS 地址；AMD 上可忽略失败。 */
    if (ioctl(vm, KVM_SET_TSS_ADDR, TSS_ADDR) < 0)
        fprintf(stderr, "warning: KVM_SET_TSS_ADDR: %s\n", strerror(errno));

    uint8_t *ram = mmap(NULL, RAM_SIZE, PROT_READ | PROT_WRITE,
                        MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (ram == MAP_FAILED)
        die("mmap(guest RAM)");

    struct kvm_userspace_memory_region region = {
        .slot            = 0,
        .flags           = 0,
        .guest_phys_addr = 0,
        .memory_size     = RAM_SIZE,
        .userspace_addr  = (uint64_t)(uintptr_t)ram,
    };
    if (ioctl(vm, KVM_SET_USER_MEMORY_REGION, &region) < 0)
        die("KVM_SET_USER_MEMORY_REGION");

    /* guest 代码：mov al,'A'; out 0xe9,al; hlt */
    static const uint8_t guest_code[] = { 0xB0, 0x41, 0xE6, 0xE9, 0xF4 };
    memcpy(ram, guest_code, sizeof(guest_code));
    printf("guest RAM: hva=%p size=0x%llx, code at gpa 0\n", (void *)ram,
           (unsigned long long)RAM_SIZE);

    int vcpu = ioctl(vm, KVM_CREATE_VCPU, 0);
    if (vcpu < 0)
        die("KVM_CREATE_VCPU");

    int run_size = ioctl(kvm, KVM_GET_VCPU_MMAP_SIZE, 0);
    if (run_size < 0)
        die("KVM_GET_VCPU_MMAP_SIZE");
    struct kvm_run *run = mmap(NULL, run_size, PROT_READ | PROT_WRITE,
                               MAP_SHARED, vcpu, 0);
    if (run == MAP_FAILED)
        die("mmap(kvm_run)");
    printf("vCPU 0 created; kvm_run mmap size = %d bytes\n", run_size);

    /* 把 vCPU 置为 16 位实模式：CS.base=0, RIP=0, CR0.PE=0, EFER=0 */
    struct kvm_sregs sregs;
    if (ioctl(vcpu, KVM_GET_SREGS, &sregs) < 0)
        die("KVM_GET_SREGS");
    struct kvm_segment flat = {
        .selector = 0, .base = 0, .limit = 0xffff,
        .type = 3, .s = 1, .dpl = 0, .present = 1,
        .db = 0, .l = 0, .g = 0,
    };
    sregs.cs = flat;
    sregs.cs.type = 11;               /* code: execute/read/accessed */
    sregs.ds = sregs.es = sregs.fs = sregs.gs = sregs.ss = flat;
    sregs.cr0 = 0x60000010;           /* PE=0（实模式）; CD/NW 按复位值 */
    sregs.cr3 = 0;
    sregs.cr4 = 0;
    sregs.efer = 0;
    if (ioctl(vcpu, KVM_SET_SREGS, &sregs) < 0)
        die("KVM_SET_SREGS");

    struct kvm_regs regs = { .rip = 0, .rflags = 0x2 };
    if (ioctl(vcpu, KVM_SET_REGS, &regs) < 0)
        die("KVM_SET_REGS");

    for (int exits = 0; exits < 8; exits++) {
        if (ioctl(vcpu, KVM_RUN, 0) < 0)
            die("KVM_RUN");

        printf("KVM_RUN -> exit_reason=%u", run->exit_reason);
        switch (run->exit_reason) {
        case KVM_EXIT_IO: {
            uint8_t *data = (uint8_t *)run + run->io.data_offset;
            printf(" (KVM_EXIT_IO) port=0x%x dir=%s size=%u data=0x%02x",
                   run->io.port,
                   run->io.direction == KVM_EXIT_IO_OUT ? "OUT" : "IN",
                   run->io.size, *data);
            if (*data >= 0x20 && *data < 0x7f)
                printf(" '%c'", *data);
            printf("\n");
            break;
        }
        case KVM_EXIT_HLT:
            printf(" (KVM_EXIT_HLT) guest 执行了 hlt\n");
            goto done;
        case KVM_EXIT_SHUTDOWN:
            printf(" (KVM_EXIT_SHUTDOWN) guest triple fault（通常是 vCPU 状态没设对）\n");
            goto done;
        default:
            printf(" (unhandled exit)\n");
            goto done;
        }
    }

done:
    munmap(run, run_size);
    close(vcpu);
    munmap(ram, RAM_SIZE);
    close(vm);
    close(kvm);
    printf("done.\n");
    return 0;
}

Step 5：三个扩展实验

  1. 触发 KVM_EXIT_MMIO：把 guest 代码换成 C6 06 00 20 42 F4（mov byte ptr [0x2000], 0x42; hlt），但只登记了 gpa 0..0xfff。访问未登记的 gpa 会触发 KVM_EXIT_MMIO（实测 exit_reason=6），在 switch 里读 run->mmio.phys_addr / is_write / data——这正是设备模型（网卡/磁盘寄存器）的入口。
  2. 触发 KVM_EXIT_IO 的 IN 方向：guest 换成 E4 E9（in al, 0xe9），KVM 返回 KVM_EXIT_IO 且 direction=IN；VMM 需要把要返回的数据写进 (uint8_t *)run + run->io.data_offset，再 KVM_RUN。
  3. 多 vCPU：再 KVM_CREATE_VCPU 一次（index=1），每个 vCPU 一个宿主线程、各有一个 kvm_run；观察两个 vCPU 的 exit 如何交错。这就是 QEMU/Firecracker 里 “one vCPU thread per guest CPU” 的最小版本。

4. QEMU：完整的机器模拟器 / VMM

4.1 定位：两种模式，只有一个才是 VMM

QEMU 官方定位是 “generic and open source machine emulator and virtualizer”，并明确区分两种用法（docs/about/index.rst#L5-L16）：

  • system emulation（softmmu）：提供一整台虚拟机的模型（CPU、内存布局、设备、固件），CPU 可以完全软件模拟（TCG），也可以交给 KVM/Xen/HVF 等 hypervisor 执行。这才是 VMM，入口在 system/main.c（system/main.c#L69-L71）。
  • user-mode emulation（linux-user/bsd-user）：只做进程级 CPU + syscall 模拟，用于在一种 CPU 上跑另一种 CPU 的二进制。它不是 VMM，入口在 linux-user/main.c（linux-user/main.c#L682），不创建 machine/设备。

4.2 两条 CPU 执行路径：TCG 与 KVM accelerator

QEMU 把 hypervisor 抽象为 accelerator（KVM、Xen、HVF、WHPX、NVMM…），外加纯用户态的 JIT —— TCG（Tiny Code Generator，docs/system/introduction.rst#L18-L49）。

TCG（纯软件）：

  • tcg_init_machine() 初始化 TB hash、tcg_init()、tcg_prologue_init()（accel/tcg/tcg-all.c#L104-L176）；
  • guest 指令先翻译成 TCG 中间操作（accel/tcg/translator.c#L122-L124），再生成 host 机器码（tcg/tcg.c#L6562-L6565）；
  • cpu_exec_loop() 查 TranslationBlock，未命中就现场翻译，随后 cpu_tb_exec() 跳入执行（accel/tcg/cpu-exec.c#L937-L989）——每条 guest 指令都由 QEMU 进程内的翻译代码执行，不经过 VT-x/SVM。

KVM（CPU 交给内核）：

  • kvm_init() 打开 /dev/kvm、do_kvm_create_vm() 调 KVM_CREATE_VM（accel/kvm/kvm-all.c#L2977），并把 address_space_memory/address_space_io 注册到 KVM memory listener（#L3092-L3095）；
  • guest 内存区段通过 KVM_SET_USER_MEMORY_REGION 注册为 KVM memslot（kvm-all.c#L380-L411）；
  • 每个 vCPU 一个 QEMU 线程，循环调 kvm_vcpu_ioctl(cpu, KVM_RUN, 0)；guest CPU 真正在内核/硬件里跑，QEMU 线程阻塞在 ioctl 上（kvm-all.c#L3445-L3482）；
  • KVM_EXIT_IO 经 kvm_handle_io() 落到 QEMU 的 address_space_io（设备模型）；KVM_EXIT_MMIO 用 address_space_rw(&address_space_memory, ...) 完成（kvm-all.c#L3527-L3544）。

分工线：CPU 执行与内存虚拟化交给 KVM；设备模型、内存布局、固件、生命周期留在 QEMU。

4.3 启动路径：先建 machine，再建 accelerator，再 board init

QEMU system 模式的启动顺序可以逐跳读出来（main → qemu_init → qemu_main_loop，system/main.c#L44-L71）：

  2. 命令行解析结束后调 qmp_x_exit_preconfig() → machine_run_board_init() → machine_class->init(machine)（system/vl.c#L2814-L2824、hw/core/machine.c#L1697-L1699）。RAM、固件、设备都是在 board init 里创建的：x86 PC 机器在 pc_init1() 里先 x86_cpus_init() 再 pc_memory_init() / pc_system_firmware_init()（hw/i386/pc_piix.c#L187-L225）。

  4. 未请求 -S 时 qmp_cont()（monitor/qmp-cmds.c#L66）→ vm_start()（system/cpus.c#L803-L806）唤醒 vCPU（autostart 调用在 system/vl.c#L2849-L2850）；主线程进入 qemu_main_loop() 的事件循环（system/runstate.c#L923-L932、util/main-loop.c#L565-L606）。主循环不执行 guest 代码，只做 poll + 定时器；CPU 执行在独立 vCPU 线程里。

4.4 设备模型：QOM/qdev、machine type、virtio/vhost、固件

  • qdev：所有设备都是 QOM 对象；qdev_realize() 是“设备生效“的边界（hw/core/qdev.c#L265-L281），MachineInitPhase 规定 cold-plug / hot-plug 的时机（include/hw/core/qdev.h#L1118-L1149）。
  • machine type：machine 类携带名称与 compat_props（hw/core/machine.c#L1219-L1225），这是 QEMU 跨版本兼容/迁移的关键机制。
  • virtio：公共实现在 hw/virtio/virtio.c（virtio_init() / virtio_add_queue() / virtio_device_realize()，hw/virtio/virtio.c#L3766、#L2567-L2577、#L4247-L4282）。
  • vhost / vhost-user：数据面可以从 QEMU 下沉到内核（vhost）或独立进程（vhost-user）：vhost_dev_start() 设置 feature 并把 guest 内存表交给后端（hw/virtio/vhost.c#L2192-L2215），三种部署形态见 docs/devel/virtio-backends.rst#L8-L15。
  • 固件/ACPI：PC 机器默认加载 bios.bin（hw/i386/pc_sysfw.c#L247-L254），ACPI 的生成在 hw/i386/acpi-build.c，SMBIOS 在 hw/smbios/ 下的 smbios.c 等文件。-kernel 直接引导时会走 x86_load_linux() 绕过固件（hw/i386/x86-common.c#L643）——这正是 microVM 式快速启动的路径。

4.5 为什么 QEMU “重”：结构性原因

“重“不是某一行代码的问题，而是四个结构性选择叠加：

  1. 设备/机器数量大：hw/ 下 71 个子目录、1481 个 .c 文件、约 81.2 万行（含头文件约 84.8 万行，v11.1.3 统计）；
  2. 固件路径完整：pc-bios/ 顶层有 73 个文件 + 6 个目录（79 个顶层条目）、roms/ 管理 14 个固件 submodule；PC 机器默认走 BIOS→ACPI→PCI 枚举；
  3. 向后兼容与迁移：migration/ 44 个 .c、约 3.5 万行；版本化 machine type 提供 6 年（18 个 release）的兼容窗口（docs/about/deprecated.rst#L14-L25）；
  4. 通用性优先：同一份 QEMU 要同时支持 TCG 与 KVM/Xen/HVF/WHPX 等多 accelerator、几十个目标架构、HMP/QMP/libvirt 等管理接口。

QEMU 自己也承认 microVM 是一条“裁剪“路线：内建的 microvm machine type 文档明说它 “without PCI nor ACPI support, designed for short-lived guests… optimized for both boot time and footprint”（docs/system/i386/microvm.rst#L7-L10）。

数字提醒：QEMU 官方没有给“启动时间 X ms / 内存开销 Y MiB“的一手数字；常被引用的对比来自 Firecracker NSDI’20 论文（测量基于当时的 QEMU 版本，结论是 microVM 启动明显快于 QEMU），属于二手来源，引用时注意时代差异。

4.6 边界：QEMU ≠ KVM，也 ≠ Firecracker

  • QEMU 可以完全不用 KVM（纯 TCG），此时连硬件虚拟化都不需要；
  • KVM 也可以不配 QEMU（Firecracker/Cloud Hypervisor/crosvm 直接消费 /dev/kvm）；
  • QEMU 和 Firecracker 是同一层（用户态 VMM）的不同取舍：通用/兼容/可迁移 vs 极小/极快/少攻击面；
  • QEMU 是 Kata 的可选 VMM 之一（并且功能覆盖最广，支持 GPU/VFIO 与 TDX/SEV-SNP），但不是唯一选择。

5. Firecracker：为 serverless 裁剪出来的 microVM

5.1 定位：只做一件事的 VMM

Firecracker 是 AWS 开源的 Rust VMM，一个进程只跑一个 microVM。官方设计文档对 microVM 的定义是：

“Firecracker microVMs combine the security and workload isolation properties of traditional VMs with the speed, agility and resource efficiency enabled by containers.”（docs/design.md#L7-L12）

官方 FAQ 把它与 QEMU 的关系讲得很直白：它是 “alternative to QEMU … purpose-built for running serverless functions and containers safely and efficiently, and nothing more”（FAQ.md#L53-L66）。它由 AWS 为 Lambda/Fargate 的多租户隔离而开发（README.md#L33-L36）。

5.3 启动流程：先 API 配置，再 InstanceStart

Firecracker 不是“命令行拉起虚拟机“，而是：起进程 → 通过 unix socket 上的 HTTP API 逐条配置 → 发 InstanceStart。

  1. PrebootApiController::build_microvm_from_requests 用 from_api.recv() 逐条处理 machine-config / boot-source / drives / network-interfaces / vsock 等请求，直到 built_vmm.is_some()（rpc_interface.rs#L375-L442）；
  2. PUT /actions {"action_type": "InstanceStart"} 被解析成 VmmAction::StartMicroVm（actions.rs#L35-L40）；
  3. start_microvm() → build_and_boot_microvm()：先 build_microvm_for_boot，再 resume_vm() 让 vCPU 真正进入 KVM_RUN（rpc_interface.rs#L652-L680、builder.rs#L399-L413）；
  4. builder 内部顺序：allocate_guest_memory() → Kvm::new → KvmVm::new（KVM_CREATE_VM）→ create_vcpus（KVM_CREATE_VCPU）→ register_dram_memory_regions（KVM_SET_USER_MEMORY_REGION）→ 依次 attach 设备；vCPU 先以 Paused 状态启动（builder.rs#L165-L205、#L242-L303、#L367-L377）。

5.4 设备模型与“无 BIOS / 无 PCI / 无 ACPI“的准确说法

Firecracker 默认只暴露极少的设备（docs/design.md#L101-L114）：

  • VirtIO net / block / vsock；
  • serial console；
  • partial keyboard controller（i8042）：唯一用途是让 guest 请求 reboot；
  • guest 还会看到 KVM 提供的 PIC、IOAPIC、PIT。

FAQ 用 “6 个 emulated devices” 概括基线（virtio-net、virtio-balloon、virtio-block、virtio-vsock、serial、keyboard，FAQ.md#L60-L66），但 v1.18.0 还支持可选的 pmem、entropy（virtio-rng）、virtio-mem（memory hotplug）等（README.md#L104-L120）；vhost-user block 后端仍是 developer preview（block-vhost-user.md）。

必须区分版本的三个说法：

说法v1.18.0 事实证据
无 BIOS/固件✅ 成立：没有 firmware/POST，linux-loader 直接把 ELF/bzImage 装入 guest memory 并设置入口arch/x86_64/mod.rs#L495-L548

取舍效果：没有固件/引导器意味着少一层启动延迟和攻击面（代价是 guest 内核必须能被直接 boot，Firecracker 维护自己的 kernel support policy）；默认没有 PCI 枚举与热插拔意味着少一套 config space 攻击面（需要更高吞吐/热插拔时用 --enable-pci 换回 PCI transport）。

5.5 KVM 使用：全部经 kvm-ioctls，自己不虚拟化 CPU

  • KvmFd::new() 打开 /dev/kvm、校验 KVM_API_VERSION、逐项 check_extension_raw（kvm.rs#L32-L46）；
  • KVM_CREATE_VM（带 EINTR 指数退避重试，vm.rs#L174-L209）、KVM_CREATE_VCPU（arch/x86_64/vcpu.rs#L175-L188）、KVM_SET_USER_MEMORY_REGION（vm.rs#L453-L475）、KVM_RUN；
  • guest 内存默认是 MAP_PRIVATE | MAP_ANONYMOUS（memory.rs#L948-L960），这也解释了它的 overcommit 与快照恢复能力。

5.6 jailer：VMM 被攻破后的第二道防线

jailer 是一个启动器：以 root 运行，先用特权把隔离环境搭好，再降权 exec 真正的 firecracker 进程（docs/design.md#L177-L184）。执行顺序（src/jailer/src/env.rs#L655-L792）：

  1. 清空继承环境：close_range(3, UINT_MAX) 关掉除 0/1/2 外的所有 fd，清空环境变量（main.rs#L257-L287）——注意这是“全关“式清理，不是 fd 白名单；
  2. 拷入可执行文件：copy（不是 hardlink）到 chroot，避免与其他 Firecracker 进程共享 .text 页（env.rs#L499-L549）；
  3. 可选 netns / rlimit / cgroup（安装顺序在 env.rs#L655-L680，cgroup 配置见 cgroup.rs#L235-L243）；
  4. mount namespace + pivot_root：unshare(CLONE_NEWNS) → MS_SLAVE → bind mount → pivot_root → umount2(MNT_DETACH) → chroot（chroot.rs#L19-L101）。比裸 chroot 强，因为旧根已卸载；
  5. 造设备节点：mknod /dev/kvm、/dev/net/tun、/dev/urandom 等（env.rs#L695-L728），最后 Command.uid/gid + exec() 降权（env.rs#L574-L577）。

重要纠正：seccomp 不是 jailer 装的。seccomp 过滤器由 Firecracker 自己按线程（vmm/api/vcpu）在进入 guest 代码前加载（vcpu.rs#L217-L226、api_server_adapter.rs#L250-L258、docs/seccomp.md#L5-L12）。jailer 负责 chroot/namespace/cgroup/rlimit/清 fd/降权；seccomp 负责限制 Firecracker 能调用的宿主 syscall。两者合起来才是“第二道防线“。

5.7 快照/恢复：File backend 按需缺页，UFFD 交给用户态

  • 两类快照：Full（全量内存 + state）与 Diff（只存 dirty pages，仍标 developer preview）（snapshot-support.md#L203-L215）；
  • 创建：create_snapshot 先 vmm.save_state() 序列化设备/KVM/vCPU 状态，再 kvm_vm.snapshot_memory_to_file(...) 写内存（persist.rs#L169-L198）；dirty 页来自 KVM dirty log 或 mincore(2) 近似（vm.rs#L600-L616）；
  • 恢复（File backend）：内存文件 MAP_PRIVATE 映射，缺页时按需从 page cache 拉页、写时 COW——不是把内存全部拷回 RAM（snapshot-support.md#L77-L86）；
  • 恢复（UFFD backend）：把 uffd fd 通过 unix socket 交给用户态 page-fault handler，由它决定预取/分页策略（persist.rs#L555-L588）。

这套能力是“同一个快照可在不同 Firecracker 进程恢复/克隆 microVM“的基础，也是高密度 serverless/agent 预热池的关键机制（仓库文档没有直接写 AWS 内部如何用，引用时需注意）。

6. Kata Containers：把容器塞进 VM 的运行时

6.1 定位：不是 hypervisor，是 OCI 运行时

Kata 官方定义：

“Kata Containers is an open source community working to build a secure container runtime with lightweight virtual machines (VM’s) that feel and perform like standard Linux containers, but provide stronger workload isolation using hardware virtualization technology as a second layer of defence.”（docs/design/architecture/README.md#L5-L10）

三个关键点：

  1. 它是 OCI 兼容的容器运行时（containerd shim v2 + 编排层），不是 VMM、不是 hypervisor；
  2. 隔离边界是 VM：每个 Kubernetes Pod 一台轻量 VM（“Kata Containers represents a Kubelet pod as a VM”，kubernetes.md#L12）；
  3. 一个 VM 里可以跑同一 Pod 的多个容器（shimv2 支持 “several containers per VM”，README#L79-L87），这正是 Pod 内共享网络/存储语义所需。

它自己不做 CPU 虚拟化，也不实现 VMM；VMM（QEMU/Cloud Hypervisor/Firecracker/Dragonball）是可替换后端，真正提供硬件隔离的是 KVM + guest 内核 + VMM。

  • initrd vs rootfs image：两种都支持（guest-assets.md#L17-L24）；4.4.0 默认 guest 磁盘从 ext4 改为压缩 EROFS（docs/releases/4.4.0.md#L62-L75）；
  • agent 作为 PID 1：initrd 场景 kernel 直接以 kata-agent 为 init（guest-assets.md#L101-L108）；rootfs image 场景 systemd 是 PID 1、agent 作为 service（guest-assets.md#L57-L66）。代码里用 getpid() == 1 判断 init 模式（src/agent/src/main.rs#L350-L356）；
  • 容器 rootfs：Go runtime 走 virtio-fs 或 9p（kataShared tag，kata_agent.go#L118-L136）；runtime-rs 按 mount 类型选择 share-fs（virtio-fs）/block/nydus/EROFS（rootfs/mod.rs#L80-L150）。

6.6 Kubernetes 接线与开销

  • RuntimeClass 名字形如 kata-<shim>，handler 默认等于该名字（runtimeclasses.yaml#L73-L93）；
  • kata-deploy 为每个 handler 写 containerd 配置：同一个 shim 二进制 + 不同 ConfigPath 指向不同 configuration-*.toml，从而同一个二进制支持多种 VMM（containerd.rs#L349-L391）；
  • Pod Overhead 是调度预留，不是 VM 内存总量：Cloud Hypervisor/Firecracker 类 130Mi、QEMU 320Mi、SEV-SNP/TDX 2048Mi、NVIDIA GPU 类 10240Mi（runtimeclasses.yaml#L11-L40）；guest RAM 默认另有 2048 MiB（runtime-rs 的 DEFMEMSZ := 2048，src/runtime-rs/Makefile#L184-L185）。

Kata 官方没有给“单 Pod 启动耗时 X ms“的统一 benchmark。能追到的一手数字是模板实验：模板恢复 vs 直接创建 0.6s vs 0.82s（相对对比，不是通用 boot time，how-to-use-template-in-runtime-rs.md#L103-L105）。引用时不要把它当绝对基线。

6.7 Confidential Containers（CoCo）

Kata 是 CoCo 的 VM 运行时底座，但 CoCo ≠ Kata：

  • TEE RuntimeClass：kata-qemu-snp（AMD SEV-SNP）、kata-qemu-tdx（Intel TDX）、kata-qemu-se（IBM SE）（kata-deploy-runtimeclasses.md#L102-L118）；4.4 默认 runtime-rs，对应还有 kata-qemu-snp-runtime-rs 等变体（#L110-L118），选型时以发布物 handler 列表为准；
  • agent 从 initdata 设备读 aa.toml/cdh.toml/policy.rego（src/agent/src/initdata.rs#L24-L38）；
  • genpolicy 从 K8s YAML 生成 OPA/Rego policy 限制 agent API 调用（src/tools/genpolicy/README.md#L3-L15）；
  • 概括：TEE 提供 CPU 侧内存加密与硬件 attestation；Kata 提供 VM 边界、guest agent、initdata 与 policy；完整 attestation 协议与密钥放行由 CoCo 的 AA/CDH 组件完成。Kata 仓库本身不是完整的 CoCo 控制面。

6.8 误区：Kata ≠ hypervisor，VM-per-Pod ≠ VM-per-Container

误解事实
“Kata 是 hypervisor/VMM”它是 OCI 运行时；VMM 是它的可替换后端
“每个容器一台 VM”标准模型是 VM-per-Pod，一个 VM 跑同一 Pod 的多个容器
“VM 里跑 runc”guest 内由 kata-agent 的 rustjail 创建 ns/cgroup；文档只是说效果等价于 runc
“320Mi overhead 就是 VM 内存”overhead 是 shim/virtiofsd/VMM 的宿主预留；guest RAM 默认另算 2048 MiB
“guest image = 容器镜像”guest image 是 VM 的 mini-OS；容器镜像才是 workload
“CoCo 就是 Kata”CoCo = Kata + TEE + attestation/initdata/policy 等组件

7. gVisor：用用户态内核替代内核

7.1 定位：不是 VM，不是 syscall 过滤器，是第三种机制

gVisor 官方介绍只有一句话：“an application kernel that implements a Linux-like interface”，用内存安全语言（Go）写成、跑在用户态（g3doc/README.md#L4-L6）。它明确把自己与两类技术区分开：

“gVisor is not a syscall filter … nor a wrapper over Linux isolation primitives … gVisor is also not a VM in the everyday sense of the term (e.g. VirtualBox, QEMU).”（g3doc/README.md#L37-L44）

架构指南里有一句更关键的：

“gVisor never passes through any system call to the host. Therefore, if a kernel feature isn’t reimplemented in gVisor, then the sandboxed workload cannot use it.”（g3doc/architecture_guide/intro_to_gvisor.md#L87-L105）

对外，runsc 实现 OCI runtime 接口（runsc/main.go#L18-L19），所以 Docker/containerd/Kubernetes 可以像选 runc 一样选 runsc——这也是它和 Kata 同处“运行时层“的原因。

  • Sentry：Linux 内核的（部分）模拟。包文档写明 “Package kernel provides an emulation of the Linux kernel.”（pkg/sentry/kernel/kernel.go#L15-L16）；
  • 调度：Sentry 不实现自己的 CPU 调度器，可调度实体映射成 goroutine，交给 Go runtime（pkg/sentry/kernel/README.md#L13-L18）；
  • syscall 路径：platform 把应用线程陷进 Sentry → Task.run → doSyscall（task_syscall.go#L209-L213）→ executeSyscall 查 O(1) syscall 表（syscalls.go#L429-L435），缺失的 syscall 走 Missing 回调；

所以和 seccomp 沙箱的分水岭是：seccomp 是“过滤哪些 syscall 可以进宿主内核“，gVisor 是“应用 syscall 根本不进宿主内核，由 Sentry 重新实现语义“。

7.3 三个 platform：systrap（默认）、KVM、ptrace

Platform 的核心抽象是执行上下文与地址空间（pkg/sentry/platform/platform.go#L39-L41）；syscall/缺页拦截由各 platform 自行实现（如 systrap 的 seccomp 规则、KVM 的缺页处理）。runsc 按配置名 platform.Lookup(conf.Platform) 选择（runsc/boot/loader.go#L1237-L1255）。

systrap 是默认，代码和文档双重确认：runsc flag 默认值直接写 "systrap"（runsc/config/flags.go#L109）；官方文档说 “systrap replaced ptrace as the default gVisor platform in mid-2023”（g3doc/architecture_guide/platforms.md#L53-L60）。

systrap 的机制细节：给工作负载线程装 seccomp filter，用户 syscall 命中后触发 SIGSYS（或页错误触发信号），信号处理 stub 把请求写进与 Sentry 共享的内存（共享区域见 syscall_thread.go#L42），Sentry 处理后再唤醒 stub（pkg/sentry/platform/systrap/README.md#L1-L27）。在 Linux 5.11+ 上它优先用 prctl(PR_SET_SYSCALL_USER_DISPATCH, ON, …)，比 seccomp 便宜，遇到 EINVAL 回落到 seccomp（systrap/subprocess.go#L299-L316）；x86 上还会把 syscall 指令改写成跳板（--systrap-disable-syscall-patching 可关）。

KVM platform 的准确说法：它让 Sentry 同时扮演 guest OS 和 VMM，应用跑在 guest ring 3；但官方明确说 “there is no virtualized hardware layer – the sandbox retains a process model”，用 KVM 只是为了改进地址空间切换的隔离与性能（g3doc/architecture_guide/platforms.md#L40-L45）。所以：gVisor 用 KVM ≠ gVisor 是 VM。在 VM 里跑（nested）时，官方反而说 systrap 常常更快。

7.4 文件系统：独立 gofer + LISAFS（不是 9P 直通）

文件访问由一个独立进程 gofer 代理，Sentry 与 gofer 之间用 LISAFS 协议：

“gVisor accesses the filesystem through a file proxy, called the Gofer. The gofer runs as a separate process, that is isolated from the sandbox. Gofer instances communicate with their respective sentry using the LISAFS protocol.”（g3doc/user_guide/filesystem.md#L5-L7）

为什么拆进程：Sentry 被设计成“可能被攻破“的组件，所以它的 mount namespace 尽量空、不直接持有 host 文件资源；由“稍微更可信“的 gofer 在稍高权限的上下文里代为访问——这是最小权限设计，不是性能选择（g3doc/architecture_guide/security.md#L142-L152）。

代码上，Sentry 侧的文件系统类型名还叫 "9p"（兼容历史），但实际 client 是 lisafs.NewClient(sock)（pkg/sentry/fsimpl/gofer/gofer.go#L76-L77、#L736）；LISAFS 的 README 说 9P2000.L 太“话痨“，所以换成了自定义的 FD-based 协议（pkg/lisafs/README.md#L5-L16）。默认开启的 directfs 进一步让 gofer 把 host FD “捐赠“给 sandbox，用 openat 等 FD-based syscall 直接操作，减少往返（g3doc/user_guide/filesystem.md#L72-L88）。

7.5 网络：netstack + 一个 AF_PACKET socket

TCP 连接状态、控制消息、组包全部在 Sentry 内实现（g3doc/user_guide/networking.md#L5-L9），代码主体在 pkg/tcpip/stack。与 host 的接线不是 tun：

“The sentry … is initialized with a single AF_PACKET socket. … gVisor ingresses and egresses all non-loopback traffic across that socket.”（g3doc/architecture_guide/networking.md#L29-L33）

host 侧由 runsc 在带 veth 的 netns 里创建 AF_PACKET socket 并把 FD 交给 sandbox（runsc/sandbox/network.go#L790-L796），sandbox 内用 fdbased link endpoint 把它变成 netstack 的 NIC（pkg/tcpip/link/fdbased/endpoint.go#L18-L21）。--network=host 会切到 hostinet、直接使用 host 网络栈，官方明确说这会降低隔离（g3doc/user_guide/networking.md#L23-L27）。

7.6 host 侧防线：给 Sentry 自己套 seccomp 白名单

这是 gVisor 的第二层防御：即使应用 syscall 被 Sentry 接管，Sentry 自己对 host 的 syscall 也要被显式枚举。

  • runsc 给 Sentry 装 seccomp filter：“Package filter installs seccomp filters to prevent prohibited syscalls in case it’s compromised.”（runsc/boot/filter/filter.go#L15-L16）；
  • 规则是白名单：allowedSyscalls 只包含 futex、clock_gettime、epoll_*、read/write、mmap 等基础 syscall，没有 execve、connect、socket（除非 host 网络）、openat（除非 directfs）（runsc/boot/filter/config/config_main.go#L25-L26）；
  • 违规默认杀进程：RET_KILL_PROCESS（pkg/seccomp/seccomp.go#L44-L48）；
  • 开启 host 网络或 nvproxy 会放宽 filter，官方会打印 warning（“host networking enabled: syscall filters less restrictive!”，runsc/boot/filter/config/config.go#L101-L121）。

设计原则三条：“No system call is passed through directly to the host”、“Only common, universal functionality is implemented”、“The host surface exposed to the Sentry is minimized”（g3doc/architecture_guide/security.md#L184-L197）。

7.7 兼容性与 GPU：能跑什么、跑不了什么

gVisor 只实现 Linux syscall ABI 的子集。官方明确的缺口（g3doc/user_guide/compatibility.md#L40-L70）：

  • in-sandbox cgroups 只能记账，不能在 sandbox 内对进程间做资源限额（要靠 host cgroup 限制整个 sandbox）；
  • 不能在沙箱内挂载块设备文件系统（fat32/ext3/ext4 等），只能 host 挂好再暴露；
  • iptables 部分支持；io_uring 默认关闭，开启也只支持基础 I/O；
  • 自定义硬件设备文件一般不支持，例外只有 NVIDIA GPU（nvproxy）与 TPU；
  • 沙箱内不能再用 KVM。

GPU 通过 nvproxy 实现：在沙箱内代理 NVIDIA 驱动的 ioctl 到 host 驱动（pkg/sentry/devices/nvproxy/nvproxy.go#L15-L19），需要 --nvproxy，且只支持选定的 NVIDIA 开源驱动版本（g3doc/user_guide/gpu.md#L11-L21）。注意路径是 pkg/sentry/devices/nvproxy，不是 pkg/nvproxy。

gVisor 官方 Performance Guide 明确写着：“Except where specified, all tests below are conducted with the ptrace platform”（g3doc/architecture_guide/performance.md#L58-L64），而 ptrace 已经不是默认、官方不再支持。所以下面这些数字是“ptrace 时代“的基线：

9. 常见误解合集

下面这些问题在讨论中最容易出现，逐条给一句话纠正（细节见对应章节）：

  1. “KVM 是一个虚拟机软件 / 可以直接跑 VM” → KVM 是内核模块 + /dev/kvm ioctl，只提供 CPU/内存虚拟化原语；没有 VMM 连一台能启动的 VM 都拼不出来（第 3 节）。
  2. “QEMU 就是 KVM / QEMU 是内核模块” → 反了。QEMU 是用户态 VMM，可用 KVM 加速，也可纯 TCG；KVM 也可不配 QEMU（Firecracker/CH/crosvm）（第 4 节）。
  3. “Firecracker 是 QEMU 的 fork” → 不是。它源自 Chromium OS 的 crosvm/rust-vmm 路线（FAQ.md#L11-L21），Rust 实现；与 QEMU 是同类不同取舍（第 5 节）。
  4. “Firecracker 没有 PCI/ACPI” → 默认走 MMIO 且 cmdline 带 pci=off，但 v1.13.0 起可用 --enable-pci；x86_64 上 ACPI 表一直构建。“没有 BIOS/固件“才成立（第 5.4 节）。
  5. “jailer 提供 seccomp” → seccomp 是 Firecracker 自己按线程在进入 guest 前加载的；jailer 负责 chroot/namespace/cgroup/rlimit/清 fd/降权（第 5.6 节）。
  6. “Kata 是 hypervisor / VMM” → Kata 是 OCI 运行时；VMM 是它的可替换后端，真正提供硬件隔离的是 KVM + guest 内核（第 6 节）。
  7. “每个容器一台 VM” → Kata 的标准模型是 VM-per-Pod，一个 VM 跑同一 Pod 的多个容器；guest 内再由 agent 用 ns/cgroup 隔离容器（第 6.1 节）。
  8. “VM 里跑的是 runc” → guest 内没有 runc 参与；kata-agent 用 rustjail 直接创建 ns/cgroup 并 exec workload，“等价于 runc“只是效果描述（第 6.2 节）。
  9. “gVisor 是 VM / 必须开 KVM” → 默认 platform 是 systrap，不需要虚拟化支持；KVM 只是三个 platform 之一（第 7.3 节）。
  10. “gVisor 就是一个 seccomp 沙箱” → seccomp 在 gVisor 里只是拦截手段和 host 侧第二层防线；应用 syscall 的语义由 Sentry 的 Go 实现决定（第 7.2/7.6 节）。
  11. “gVisor 完全兼容 Linux” → 只实现 syscall 子集：io_uring 默认关、块设备文件系统不能挂、/proc 与 /sys 部分实现、自定义设备仅 GPU/TPU（第 7.7 节）。
  12. “microVM 没有内核 / 就是容器” → microVM 是设备极简的 VM，有独立 guest 内核；它只是启动快、设备少（第 5 节）。
  13. “用了 VM 就一定安全” → VM 边界更强，但攻击面还包括 VMM/设备模型（virtio）、固件和配置；需要纵深防御（jailer、seccomp、最小设备）（第 5.6 节）。
  14. “RuntimeClass 会提供隔离” → 它只选择 handler + 调度约束 + 开销声明；隔离来自 handler 指向的运行时（第 8.4 节）。
  15. “官方性能数字可以直接引用” → gVisor 官方性能页用的是 ptrace（已非默认），Firecracker 125ms 是 InstanceStart→init 而非进程启动时间，Kata 没有通用 boot time 数字；引用时必须带口径（第 5.8/6.6/7.8 节）。

10. 名词速查

10.1 虚拟化基础

名词含义常见误解
host / guest宿主（跑 VMM 的机器）/ 客户机（VM 里的系统）“guest 就是容器”——不是，guest 是完整内核
VMM / hypervisor创建并运行 VM 的软件层（见 §0.3）常把 KVM 当成 VMM；KVM 只是内核 API，QEMU/Firecracker 才是 VMM
vCPU虚拟 CPU，一个宿主线程 + 一个 KVM vCPU fd不是“一个核“，vCPU 与宿主线程的映射由 VMM 决定
VT-x / AMD-VIntel / AMD 的硬件虚拟化扩展没有它也能用 QEMU（TCG），只是纯软件模拟
VMX root / non-rootCPU 的两种运行模式：宿主在 root，guest 在 non-rootguest 内的 ring0 在 non-root 下没有真实特权
VMCS保存 VM 进出状态的控制结构（x86）不是内存页表
VM exitguest 执行到需要 VMM 处理的操作时，CPU 切回 root 模式“VM exit 就是中断”——不准确，是受控的特权切换
EPT / NPT第二代地址翻译（stage-2），把 guest 物理地址映射到宿主物理地址和 guest 自己的页表（stage-1）是两层
TCGQEMU 的动态二进制翻译器（纯软件模拟 CPU）“TCG 等于模拟器全部”——TCG 只负责 CPU 指令
microVM设备模型极简、启动快、内存小的 VM“microVM 是容器”——不是，它有独立 guest 内核
virtio半虚拟化 I/O 标准（guest 驱动 ↔ 宿主后端）不是直通；直通是 VFIO/device assignment
vhost / vhost-user把 virtio 后端从 QEMU 进程搬到内核或独立进程“virtio 一定要 QEMU”——vhost-user 可完全脱离 QEMU
vsock宿主与 guest 之间的 socket（不经过 IP 网络）只适合控制面/小数据，不等同于网络设备
MMIO / PIO内存映射 I/O / 端口 I/O，guest 访问设备的方式都会触发 VM exit（除非硬件加速）
快照 / 恢复保存 VM 或进程的内存+设备状态，之后恢复gVisor 的快照是进程检查点，Firecracker 的快照是 VM 状态
UFFDuserfaultfd，按需缺页加载，常用于快照恢复时懒加载内存不是快照格式本身
seccomp用 BPF 限制进程能调用的宿主 syscall它是过滤器，不是隔离内核；gVisor 的 systrap 用它来拦截
jailerFirecracker 的启动器：chroot/namespace/cgroup/rlimit/清继承 fd/降权（seccomp 由 Firecracker 自己装）不是 VMM 的一部分，是 VMM 的“笼子“
