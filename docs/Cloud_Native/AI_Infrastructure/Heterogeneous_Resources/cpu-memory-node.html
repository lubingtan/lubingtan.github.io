CPU、内存与节点资源基础

结论先行：Kubernetes 的 requests 和 limits 不是同一件事。request 主要影响调度、QoS 和 保护水位；limit 才由内核通过 cgroup 强制执行。CPU 是「可压缩」资源，超限表现为 throttling； 内存是「不可压缩」资源，超限表现为 reclaim/OOM。把二者当成同一种「配额」来配，是节点抖动、 容器被 throttle、Pod 被 OOMKilled 的最常见来源。

这一篇先把 L0 讲清楚：cgroup v1/v2 的字段映射、CPU quota 与 cpuset、内存压力与 eviction、 以及 CPU Manager / Memory Manager / Topology Manager 的真实作用与边界。后面 GPU 的 NUMA 对齐、MIG 切片、训推混部，都是建立在这些语义之上的。

一、requests / limits 到底分别由谁执行

维度requestslimits
主要作用调度器选节点；QoS 分类；kubelet 计算保护水位/OOM score内核 cgroup 强制执行上限
CPU转成 cpu.weight（v2）或 cpu.shares（v1）；只决定「竞争时的相对份额」转成 cpu.max（v2）或 cfs_quota_us+cfs_period_us（v1）；超限被 throttle
内存默认不在 cgroup 里预留；只影响调度和 OOM score。开启 MemoryQoS 的 TieredReservation 后才写 memory.min/memory.low转成 memory.max；超限触发 cgroup 内 OOM kill
超卖可以超卖（节点 request 总和 ≤ allocatable 是调度约束，不是内核约束）不可超卖；limit 是硬上限
典型误解「request 小一点没关系，反正 limit 大」「limit 设了就不会 OOM」——内存 limit 是反应式的，只有内核检测到压力才杀

Kubernetes 文档对二者的区别有一个很准确的表述：CPU limit 由 CPU throttling 强制执行，是硬限制； memory limit 由 OOM kill 强制执行，是反应式的，容器可能先超过 limit，然后在内存压力下被杀。 见 Resource Management for Pods and Containers。

kubelet 把 API 里的 quantity 翻译成 runtime 资源结构的关键代码在 calculateLinuxResources： CPU request → CpuShares，CPU limit → CpuQuota/CpuPeriod，memory limit → MemoryLimitInBytes。 真正的 cgroup 写入由 runtime（containerd + runc）完成。

一个容易忽略的点：如果只写 limit 不写 request，API server 会把 request 默认成 limit （除非有 LimitRange 等准入机制另设）。所以「只设 limit」通常等价于「request = limit」， 会直接改变 QoS 和调度结果。

二、QoS：不是标签，是调度与驱逐的输入

QoS判定条件CPU 行为内存行为驱逐/OOM 优先级
Guaranteed每个容器（或 Pod 级 resources）CPU、memory 的 request 都等于 limit，且都 > 0整数 CPU 可被 static CPU Manager 独占最不容易被驱逐；OOM score 最低最后
Burstable不满足 Guaranteed，但至少一个容器/Pod 有 CPU 或 memory 的 request/limit共享池；有 limit 时受 CFS quota有 limit 时受 memory.max；OOM score 按 request 比例中间
BestEffort所有容器/Pod 都没有 CPU、memory 的 request/limit共享池，无 quota无 limit；最容易 OOM最先

判定与驱逐顺序见 Pod QoS Classes。 注意：QoS 不直接决定 kubelet 的驱逐顺序。kubelet 的排序是「是否超过 request → Priority → 超过 request 的程度」；QoS 只是让你预判谁更可能超过 request。文档明确写了 The kubelet does not use the pod's QoS class to determine the eviction order.

2.1 Pod 级 resources 与 effective request

从 1.34 起 Pod 级 spec.resources 是 Beta 默认开启；1.37 中 Pod 级 resource managers （CPU/Memory/Topology 使用 Pod 级 resources）还是 Beta 但默认关闭。两者不要混为一谈。

Pod 的 effective request 不是简单把容器加起来：

effective_init = max over init 容器 i ( request(i) + 它之前已启动的 sidecar 的 request )
effective_steady = sum(所有非 init 容器，即 app + sidecar)
effective = max(effective_init, effective_steady) + pod overhead

原因：init 容器逐个运行，sidecar 在 init 阶段就已经常驻。调度按 effective request 预留， 所以「init 容器申请很大」会抬高整个 Pod 的调度请求，即使稳态用不到。详见 Effective Pod requests and limits。

GPU 训练/推理里的 sidecar（日志、监控、模型加载、KV cache 预热）很容易把 effective request 抬高一个档位；如果节点只按「稳态」估算容量，就会出现调度不上或节点实际超卖。

三、cgroup v1 与 v2：同一语义，不同字段

Kubernetes 同时支持 cgroup v1 和 v2。v2 是统一层级（unified hierarchy），CPU/内存/IO 控制器挂在 同一棵树上；v1 是每个控制器一棵树。字段映射如下（以 kubelet 实际写入为准）：

语义cgroup v1cgroup v2说明
CPU 相对份额cpu.sharescpu.weightv2 权重范围 1–10000，默认 100；kubelet 在两者间做近似换算
CPU 带宽上限cpu.cfs_quota_us + cpu.cfs_period_uscpu.max（$MAX $PERIOD）默认 period 100ms；max 表示不限
CPU 统计cpu.statcpu.stat / cpu.stat.local都有 nr_periods、nr_throttled、throttled_usec
CPU 压力无统一接口cpu.pressurePSI，见后文
CPU 亲和cpuset.cpuscpuset.cpus / cpuset.cpus.effectiveCPU Manager 写的是前者
内存 NUMA 亲和cpuset.memscpuset.mems / cpuset.mems.effectiveMemory Manager 写的是前者
内存硬上限memory.limit_in_bytesmemory.max超限触发 cgroup 内 OOM
内存软限制memory.soft_limit_in_bytesmemory.lowv2 的语义更明确：best-effort 保护
内存硬保护无memory.min内核在保护范围内不回收；过度保护会导致 OOM
内存节流无memory.high超过后节流 + 强回收，但不触发 OOM
内存事件memory.failcnt 等memory.eventslow/high/max/oom/oom_kill 计数
OOM 整组杀无memory.oom.group1 表示 cgroup 内进程整组杀
PID 上限pids.maxpids.max防 fork bomb

内核语义以 cgroup v2 文档 为准。几个关键定义：

  • memory.min（硬保护）：使用量在 min 以内时，内核不会回收该 cgroup 的内存； 如果系统没有可回收的无保护内存，就触发 OOM。把超过实际可用的内存设成 min，会导致持续 OOM。
  • memory.low（软保护）：使用量在 low 以内时，只有在没有无保护内存可回收时才回收； 是「尽量不回收」，不是「绝不回收」。
  • memory.high（节流）：超过后进程被节流并承受强回收压力；永远不会触发 OOM， 极端情况下可以被突破。适合「先降速、别杀」的场景。
  • memory.max（硬上限）：主要限制手段；达到后无法回收就在 cgroup 内触发 OOM。
  • memory.events：观察 high、max、oom、oom_kill 的第一手证据。

四、CPU：quota、throttling 与 cpuset

4.1 CPU limit 如何变成 throttling

假设容器 limits.cpu = 200m，默认 period 100ms，则 quota = 20ms/100ms。容器内多线程在 一个 period 的前 20ms 把配额跑完，剩余 80ms 就会被内核挂起，直到下一个 period。 这就是为什么：

  • 平均 CPU 使用率只有 20% 的容器，也可能出现严重 throttling；
  • 延迟敏感服务（推理、网关、tokenizer）的 p99 会在 quota 边界上跳变；
  • 把 limits.cpu 设得太低，比不设 limit 更容易造成尾延迟。

诊断：

# 找到容器 cgroup（cgroup v2）
crictl inspect <container-id> | jq '.info.runtimeSpec.linux.cgroupsPath'
# 读取节流统计
cat /sys/fs/cgroup/<path>/cpu.stat
#   nr_periods 12345
#   nr_throttled 678
#   throttled_usec 45678901
cat /sys/fs/cgroup/<path>/cpu.max
#   20000 100000

# 节点/容器级 PSI
cat /sys/fs/cgroup/<path>/cpu.pressure

nr_throttled / nr_periods 是「有多少个 period 被节流」；throttled_usec 是累计被压住的时间。 两者都要看趋势，不要只看单点。

4.2 CPU Manager：static 策略

默认 none 策略：所有容器共享 CPU 池，靠 CFS 调度和 quota。static 策略则把 Guaranteed Pod 中整数 CPU request 的容器放到独占 cpuset：

条件（源码注释写得最清楚）：

  1. Pod QoS 是 Guaranteed；
  2. CPU request 是正整数；
  3. 容器不在共享池里（BestEffort/Burstable/小数 CPU 的 Guaranteed 仍在共享池）。

static 策略要求节点有大于 0 的 CPU 预留（--kube-reserved/--system-reserved 或 --reserved-cpus），否则共享池会被独占分配吃空。CPU 池被分成三块：

池内容谁用
SHARED初始为节点所有 CPU（包含 RESERVED；启用 strict-cpu-reservation 时先移除 RESERVED）BestEffort、Burstable、小数 CPU 的 Guaranteed
RESERVEDceil(system-reserved.cpu + kube-reserved.cpu)，或 --reserved-cpus 显式列表系统守护进程、kubelet、runtime
ASSIGNABLE总 CPU − RESERVED（从 SHARED 扣除 RESERVED；strict 时 SHARED 已先移除 RESERVED）只给独占容器分配

默认（未启用 strict-cpu-reservation）RESERVED 仍留在 SHARED 里，BestEffort/Burstable 可以运行； strict-cpu-reservation 才把它们从共享池彻底移除。

源码见 policy_static.go， CPU 亲和写入 cgroup 的路径见 internal_container_lifecycle_linux.go。

常用 policy options（1.37 基线）：

选项成熟度作用代价/边界
full-pcpus-onlyGA只分配完整物理核，避免 SMT 兄弟核被不同容器占用可能降低可分配密度
distribute-cpus-across-numaBeta需要跨 NUMA 时，把 CPU 均匀分散到多个 NUMA与 full-pcpus-only 可叠加
align-by-socketAlpha按 socket 边界对齐，而不是 NUMA 边界需要开启 Alpha options gate
distribute-cpus-across-coresAlpha把 SMT 线程分散到不同物理核与 full-pcpus-only 互斥
strict-cpu-reservationGA把 reserved CPUs 从共享池中彻底移除共享池变小；需删 state 文件重启
prefer-align-cpus-by-uncorecacheGA尽量按 uncore cache 边界对齐尽力而为，不保证

几个必须知道的边界：

  • 独占只对 Pod 之间生效。文档明确写：kubelet、runtime 等系统服务仍可能运行在这些 exclusive CPUs 上；CPU Manager 不是 isolcpus，也没有设置 cpuset.cpus.partition=isolated。 要更强的隔离，需要内核启动参数（isolcpus、nohz_full、rcu_nocbs）+ IRQ 亲和 + 实际验证。
  • 1.37 中 exclusive CPUs 不再受 CFS quota 限制。DisableCPUQuotaWithExclusiveCPUs 已锁定为 true（1.36 Deprecated，1.37 LockToDefault），所以整数 CPU 的 Guaranteed 容器 不会因为 quota 被 throttle；但共享池容器仍然会。
  • state 文件是硬约束。/var/lib/kubelet/cpu_manager_state 记录分配；切换策略（none→static） 或修改 reserved 后不删 state，kubelet 会拒绝启动并提示 drain + 删除 state 文件。
  • reconcile 有窗口。CPU Manager 周期性 reconcile（默认 10s），刚分配的容器在窗口内 可能仍与共享池有短暂重叠；对延迟极端敏感的场景要考虑这个窗口。
  • 不支持 CPU 热插拔。文档明确写了 CPU Manager 不支持运行时 offline/online CPU。

4.3 cpuset 不是全部隔离

即使容器被 pin 到 CPU 0-3，仍可能受到：

  • 系统守护进程、IRQ、内核线程在同一 CPU 上运行；
  • 同 physical core 的 SMT 兄弟线程（如果没开 full-pcpus-only）被另一个容器占用；
  • 共享 LLC/uncore cache、内存带宽、NUMA 互连；
  • CPU 频率/功耗管理（turbo、C-state）带来的抖动。

所以「CPU 独占」是调度域隔离，不是「性能隔离保证」。真正做低延迟，需要把 cpuset、IRQ、NUMA、内存带宽、SMT 和频率策略一起考虑。

五、内存：保护、节流、硬上限与压力

5.1 cgroup v2 的四个水位

memory.min   ── 硬保护：不回收；过度保护 → OOM
memory.low   ── 软保护：尽量不回收
memory.high  ── 节流：降速 + 强回收；不杀
memory.max   ── 硬上限：回收不了就 OOM

Kubernetes 的默认行为很重要：

配置默认效果
memory.max由 limit 设置容器的硬上限
memory.highmemoryThrottlingFactor 默认 nil默认不设置 memory.high，即不节流
memory.min / memory.lowmemoryReservationPolicy 默认 None默认不设置保护
memory.oom.groupcgroup v2 上默认设为 1（SingleProcessOOMKill 未配置时 kubelet 取 false）；cgroup v1 无此文件cgroup v2 默认整组杀，避免容器内只死一个进程留下坏状态；显式设 SingleProcessOOMKill=true 可恢复单进程行为

MemoryQoS 在 1.37 是 Beta 且默认开启，但它只是「允许使用」这些机制；要真正生效，必须显式配置 memoryThrottlingFactor 和/或 memoryReservationPolicy: TieredReservation。文档写得很清楚： The default kubelet configuration does not enable memory throttling or memory protection.

5.2 MemoryQoS 的两个旋钮

节流（memoryThrottlingFactor，0 < f ≤ 1）：

memory.high = floor[(request + f × (limit - request)) / pageSize] × pageSize

如果 Burstable 容器没有 memory limit，则用 node allocatable 替代 limit。Guaranteed 容器 request == limit，不设 memory.high。例如 request 256Mi、limit 1Gi、f=0.9， memory.high ≈ 947Mi。

分层保护（memoryReservationPolicy: TieredReservation）：

  • Guaranteed Pod：memory.min = request（硬保护）；
  • Burstable Pod：memory.low = request（软保护）；
  • BestEffort：不设保护；
  • 同时给 kubeps.slice 等祖先 cgroup 设置聚合保护，否则子 cgroup 的保护无效。

源码见 kuberuntime_container_linux.go 和 qos_container_manager_linux.go。

重要警告：Guaranteed 的 request == limit，所以 memory.min == memory.max。 如果工作负载有大量 page cache，内核可能来不及回收就到 memory.max，反而更容易 OOM。 文档专门提示：limit 要给 page cache 留余量。见 Memory QoS 的 Caution。

5.3 怎么读内存压力

优先级从高到低：

  1. memory.events：high 增多说明在节流；max 增多说明摸到硬上限；oom_kill 是实际被杀。
  2. memory.current / memory.peak：当前/峰值使用量；memory.peak 可 reset。
  3. PSI memory.pressure：some avg10/60/300 表示有任务因内存停顿的时间比例； full 表示所有可运行任务都停顿。比「使用率」更接近「用户体验」。
  4. memory.stat：anon、file、inactive_file、active_file、slab 等，用于判断 是匿名内存涨还是 page cache 涨。
  5. 节点 memory.available：kubelet 的驱逐信号，不等于 free。
cat /sys/fs/cgroup/<path>/memory.current
cat /sys/fs/cgroup/<path>/memory.peak
cat /sys/fs/cgroup/<path>/memory.events
cat /sys/fs/cgroup/<path>/memory.pressure
grep -E '^(anon|file|inactive_file|active_file|slab) ' /sys/fs/cgroup/<path>/memory.stat

memory.available 的计算（Linux）：node.status.capacity[memory] - node.stats.memory.workingSet， 其中 workingSet 会排除 inactive_file。这意味着 page cache 很多时，free 很低但 memory.available 可能仍然健康；反过来，active_file 会被当作不可回收，可能误触发压力。 详见 Node-pressure Eviction。

5.4 节点可分配量与 eviction

Node Allocatable = Node Capacity
                 - kubeReserved
                 - systemReserved
                 - evictionHard thresholds
                 (内存还要减去预分配的 hugepages)

Capacity 来自 /proc/meminfo 的 MemTotal，不是物理内存条容量；内核/固件在启动时保留的内存 不算。见 Reserve Compute Resources。

默认硬驱逐阈值（Linux）：

信号默认阈值
memory.available100Mi
nodefs.available10%
nodefs.inodesFree5%
imagefs.available15%
imagefs.inodesFree5%

源码见 defaults_linux.go。

  • 硬驱逐：无 grace period，立即杀 Pod；
  • 软驱逐：evictionSoft + evictionSoftGracePeriod，超过阈值持续一段时间才驱逐；
  • evictionPressureTransitionPeriod 默认 5m，防止节点条件抖动；
  • kubelet 默认每 10s 评估一次；短时间暴涨可能来不及，直接触发内核 OOM；
  • kernelMemcgNotification 可以更早收到 memcg 阈值通知。

驱逐排序（不是按 QoS）：

  1. BestEffort 或 Burstable 中超过 request 的 Pod；
  2. 按 Priority、再按超过 request 的程度；
  3. Guaranteed 和未超过 request 的 Burstable 最后，按 Priority。

5.5 三种 OOM 必须分清

类型触发者典型信号影响范围处理方向
容器 cgroup OOM内核 memcg（memory.max）OOMKilled、exit 137、memory.events oom_kill单容器/单 Pod调 limit/request、查泄漏、加 headroom

三者的关键区别：GPU 显存 OOM 不会让 kernel OOM killer 杀容器，Pod 可能仍然是 Running， 只是训练进程崩了；反过来，容器 OOMKilled 也不是 GPU 显存不够。把它们混为一谈会导致 「加内存 limit」这种完全无效的处置。

六、Memory Manager 与 Topology Manager：只做 NUMA 对齐

6.1 Memory Manager 的真实职责

--memory-manager-policy=Static 只对 Guaranteed Pod 生效，做两件事：

  1. 按 NUMA 节点分配 memory/hugepages 的「块」，给 Topology Manager 提供 hint；
  2. 把分配结果写成容器的 cpuset.mems，把内存访问限制在指定 NUMA 节点。

它不设置 memory.max，不限制内存用量，不保证内存带宽。真正的用量上限仍然是 cgroup。 源码见 policy_static.go 和 internal_container_lifecycle_linux.go。

启用 Static 必须配 --reserved-memory，且满足：

Σ reservedMemory[i] = kubeReserved.memory + systemReserved.memory + evictionHard.memory.available

不满足 kubelet 会启动失败。默认 evictionHard 的 100Mi 也要算进去，这是最常见的配置错误。 详见 Memory Manager。

6.2 Topology Manager：hint 的协调者，不是放置执行者

Topology Manager 不直接分配 CPU/内存/设备；它收集各 Hint Provider（CPU Manager、Memory Manager、 Device Manager）的 NUMA hint，按 policy 合并，决定「是否允许这个 Pod 在这台节点上启动」。

Policy行为失败表现
none不做对齐无
best-effort选择最优 hint，但不满足也允许可能跨 NUMA，性能下降
restrictedhint 必须是 preferred，否则拒绝Pod 被 kubelet 拒绝，进入 Terminated/Failed，调度器不会自动重调度
single-numa-node必须落在单个 NUMA 节点，否则拒绝同上

Scope：

  • container（默认）：每个容器单独对齐；
  • pod：整个 Pod 的所有容器对齐到同一组 NUMA 节点，适合 gang/紧耦合负载。

关键边界：

  • Topology Manager 只看 hint provider 提供的信息。device plugin 的 TopologyInfo 只有 NUMANode.ID，没有 NVLink/PCIe 距离；所以 Topology Manager 不会因为两张卡在同一 NVLink 域而优先选择它们。GPU 间的 NVLink 拓扑要靠 DRA 属性/自定义调度器/应用自己处理。
  • 它只做准入，不做迁移。restricted/single-numa-node 拒绝后，Pod 会进入失败状态， 调度器不会自动换节点；需要用 Deployment/Job 重建，或外部控制器处理。
  • 它不保证带宽。NUMA 对齐减少跨 socket 访存，但不隔离内存带宽、LLC、PCIe 带宽。
  • NUMA 距离默认不感知。多 socket/多 NUMA 系统上，跨 NUMA 的「最优」可能很差； prefer-closest-numa-nodes=true 才会优先选择距离近的节点组合（1.32 GA）。
  • max-allowable-numa-nodes 默认 8。NUMA 节点数超过该值时 Topology Manager 会拒绝； 可以用 policy option 提高该值（必须 ≥ 8，超过 8 只告警），所以不是永久硬上限。源码 defaultMaxAllowableNUMANodes = 8，但 NewPolicyOptions 允许调大。

八、设计检查清单

  • 每个容器都有 request；延迟敏感服务不要用「只设 limit」的写法。
  • CPU limit 是否真的必要？如果设置，是否验证过 p99 和 nr_throttled？
  • 内存 limit 是否给 page cache/allocator 留了 headroom？是否开了 MemoryQoS？开了之后是否验证过 memory.events？
  • 节点是否配置了 kubeReserved/systemReserved/evictionHard？三者和是否与 reservedMemory 一致？
  • 是否需要 CPU 独占？如果需要，reserved-cpus/strict-cpu-reservation/full-pcpus-only 是否配套？
  • 是否需要 NUMA 对齐？topologyManagerPolicy 与 memoryManagerPolicy 是否同时配置？reservedMemory 公式是否满足？
  • 是否误以为 Topology Manager 会按 NVLink/PCIe 放置？如果是，改用 DRA 属性或应用级拓扑。
  • 是否把 free 当作可用内存？是否用 memory.available/PSI/memory.events 做过验证？
  • OOM 告警是否能区分容器 OOM、节点 OOM、GPU 显存 OOM？
