GPU 运维与故障处置

结论先行：GPU 故障处置的第一原则是先定故障域，再决定动作。同一个 nvidia-smi 失败， 可能是驱动没加载、容器没注入、MIG cap 缺失、Xid 79 掉总线，也可能是节点 OOM。 第二原则是不要把某个错误码直接等同硬件报废：Xid 13/31 常是应用越界，Xid 63/64 是行重映射 过程，Xid 94 是「已遏制」错误，只有 Xid 95/140 等才要求重置/进一步 RMA 评估。

第三原则是停止新分配 ≠ 驱逐已有 Pod。device plugin 标记 unhealthy 只降低 allocatable， 已分配 Pod 仍留在故障卡上；真正的隔离要靠 cordon/drain、device taint、Kueue stopPolicy 或直接删除工作负载。

二、掉卡与设备不可见

2.1 症状

  • nvidia-smi：No devices were found、Failed to initialize NVML；
  • lspci 能看到 NVIDIA 设备，但 /dev/nvidia* 不存在；
  • Node 上 GPU capacity 变为 0，或 device plugin CrashLoop；
  • Pod 卡在 ContainerCreating，事件里有 Allocate failed / failed to get allocate response；
  • 容器 Running，但 nvidia-smi -L 报 No devices were found。

2.2 分层排查

# 1) PCIe 层：设备还在不在？
lspci -Dnn | grep -i nvidia
lspci -tv | grep -i nvidia
dmesg -T | grep -i -E 'nvrm|nvidia|pcie|aer' | tail -100

# 2) 驱动层：模块/设备节点/版本
lsmod | grep nvidia
cat /proc/driver/nvidia/version
ls -l /dev/nvidia*
nvidia-smi -L

# 3) 插件层
kubectl -n kube-system logs <nvidia-device-plugin-pod> --tail=200
kubectl get node <node> -o json | jq '.status.capacity, .status.allocatable'
kubectl get node <node> --show-labels | tr ',' '\n' | grep nvidia

# 4) 容器层
kubectl exec <pod> -- ls -l /dev/nvidia* 2>&1
kubectl exec <pod> -- nvidia-smi -L 2>&1
crictl inspect <container-id> | jq '.info.runtimeSpec.mounts, .info.runtimeSpec.linux.resources.devices'

2.4 Xid 79：掉总线

Xid 79 的定义是：驱动尝试通过 PCIe 访问 GPU，但 GPU 不可访问。NVIDIA 文档说通常由 PCIe 链路硬件故障导致，也可能是 GPU 硬件故障或其他驱动问题。

处置：

  1. 不要反复 reset。如果是 PCIe 链路问题，reset 不会恢复，反而可能丢证据；
  2. 抓 lspci -vv、dmesg（AER/PCIe）、BMC SEL、GPU BDF/UUID；
  3. cordon/drain 节点，停止新分配；
  4. 尝试一次冷重启（不是热 reset）；如果仍不出现，走硬件诊断/RMA；
  5. 如果是 NVSwitch/整机，检查同 NVLink 域的 peer GPU 和 switch。

三、Xid：先分组，再决定动作

Xid 是 NVIDIA 驱动报告的错误码，不是「硬件坏了」的同义词。NVIDIA 官方把常见 Xid 分成了 应用错误、ECC、NVLink、GSP、掉总线等类别。下面只列高频且处置差异大的。

Xid含义常见归因建议动作是否等同报废
13GR：SW 通知错误（越界/非法指令等）应用 bug；硬件罕见compute-sanitizer/cuda-gdb 定位；修应用❌
31FIFO：MMU 错误（非法地址）应用 bug；驱动/硬件罕见同上❌
43Reset Channel Verification Error（部分工具标签为 GPU stopped processing）；GPU 仍健康应用软件故障修应用；GPU 无需处置❌
45Preemptive cleanup, due to previous errors（常见于 Ctrl-C/SIGKILL 终止 CUDA 进程）用户/系统操作正常清理；无需处置❌
48DBE（双位 ECC，不可纠正）显存硬件/瞬态GPU reset 或节点重启；查 ECC 计数◐
63/64ECC 行重映射成功/失败显存退化查 ROW_REMAPPER；64 + 失败标志 → 现场诊断/RMA◐
74NVLink 错误链路、peer GPU、NVSwitchreset 两端；查 nvidia-smi nvlink -e；反复出现找厂商◐
79GPU 从总线脱落PCIe 链路/GPU 硬件冷重启/reseat/RMA；不要热 reset 循环◐
94受控（contained）ECC 错误单应用重启该应用；方便时 reset；其他应用不受影响❌
95未受控（uncontained）ECC 错误多应用先 reset GPU，再重启应用◐
119/120GSP RPC 超时/GSP 错误固件/驱动/硬件reset/断电重启；反复出现按调试指南◐
140不可恢复 ECC，无法行重映射/页面下线显存硬件reset；仍复现 → RMA◐
121C2C 链路已纠正错误（Grace）可纠正无操作影响；维护窗口 reset 重新训练链路❌
137NVLink FLA 权限错误应用非法 P2P 访问；驱动/硬件罕见compute-sanitizer；检查 P2P 使用❌

「◐」表示「可能是硬件，但需要进一步诊断，不能仅凭这个码报废」。NVIDIA 文档对 79 也明确说 可能是 GPU 硬件故障或其他驱动问题；对 74 说可能是链路本身，也可能是链路远端设备。

3.1 处置原则

  1. 先看是否 contained：94 通常只影响一个应用；95 影响多个应用，必须先 reset。
  2. 区分「应用错误」和「硬件错误」：13/31/43/45/109/137 优先查应用；不要直接换卡。
  3. 区分「过程」和「结果」：63/64 是行重映射过程；64 失败才是 RMA 评估信号。
  4. 不要用单一 Xid 做自动化报废：至少结合 ECC、ROW_REMAPPER、dcgmi diag、复现次数、 同卡/同节点相关性。

3.2 device plugin 默认忽略哪些 Xid

NVIDIA device plugin 默认把以下 Xid 视为「应用错误，GPU 仍健康」，不标记 unhealthy：

13, 31, 43, 45, 68, 109

见 health.go。

可以通过环境变量调整：

  • DP_DISABLE_HEALTHCHECKS=all 或逗号分隔的 Xid 列表：禁用/忽略；
  • DP_ENABLE_HEALTHCHECKS=<xid>：显式启用某些 Xid；
  • 注意：这是节点级配置，改错会让整批卡的健康检测失效。

四、ECC 与行重映射：不要看到一个计数就报废

4.1 基本概念

概念含义影响
SBE（single-bit ECC）可纠正单位错误通常不影响运行；持续增长要关注
DBE（double-bit ECC）不可纠正双位错误可能触发 Xid 48/94/95/140；需要 reset/评估
volatile自上次驱动加载以来的计数重启后清零
aggregate生命周期累计计数用于长期趋势/RMA
page retirement动态页面下线（Ampere 之前/部分场景）有问题的页不再分配；可能有软件可见空洞
row remappingAmpere+ 用备用行替换退化行需要 reset 生效；不产生地址空洞

NVIDIA 文档强调：动态页面下线让大多数不可纠正 ECC 错误无需 GPU reset 即可恢复； 行重映射需要 reset 才生效，并且是持久的。见 GPU Memory Error Management。

4.2 查什么

nvidia-smi -q -d ECC
nvidia-smi -q -d ROW_REMAPPER
nvidia-smi -q -d PAGE_RETIREMENT
nvidia-smi --query-gpu=uuid,ecc.errors.uncorrected.volatile.total,ecc.errors.uncorrected.aggregate.total --format=csv

DCGM 对应字段：

字段ID含义
DCGM_FI_DEV_ECC_SBE_VOL_TOTAL310易失性 SBE 总数
DCGM_FI_DEV_ECC_DBE_VOL_TOTAL311易失性 DBE 总数
DCGM_FI_DEV_ECC_SBE_AGG_TOTAL312累计 SBE
DCGM_FI_DEV_ECC_DBE_AGG_TOTAL313累计 DBE
DCGM_FI_DEV_ROW_REMAP_UNCORRECTABLE_TOTAL393因不可纠正错误重映射的行数
DCGM_FI_DEV_ROW_REMAP_CORRECTABLE_TOTAL394因可纠正错误重映射的行数
DCGM_FI_DEV_ROW_REMAP_FAILED395行重映射失败标志
DCGM_FI_DEV_ROW_REMAP_PENDING396行重映射待生效

见 dcgm_fields.h 与 dcgm_fields.h 的 row remap 段。

4.3 RMA 判断

NVIDIA 的 RMA 策略阈值不是「出现一个 DBE 就换卡」，而是：

  • 行重映射失败标志被设置，并经现场诊断验证；
  • 例如同一 bank 上已经重映射了 8 个不可纠正错误行，再尝试重映射会触发失败标志；
  • 具体阈值和诊断流程以 NVIDIA 现场诊断工具/文档为准。

见 Row Remapping 的 RMA 策略阈值。

实务建议：

  1. 记录 volatile 与 aggregate 两个维度，不要只看一个；
  2. 记录错误发生在哪个 bank/row/页（如果工具提供）；
  3. 做一次 dcgmi diag -r 2（需要独占 GPU）或厂商现场诊断；
  4. 如果 ROW_REMAP_FAILED=1 或 Xid 95/140 反复出现，再走 RMA；
  5. 单次 SBE、单次 63/64 不应直接报废。

# 宿主机

5.3 处置

  • 内核模块 vs 用户态：统一驱动版本；reload 模块或重启节点。不要只重启 device plugin。
  • CUDA runtime vs driver：升级 driver，或在镜像里用匹配的 CUDA 版本/forward compatibility 包； 注意 forward compatibility 包不是万能的，生产要验证。
  • toolkit/CDI 版本：升级 toolkit 后重新生成 CDI spec；GPU Operator 会自动做，手工安装要手动做。
  • MIG 模式：切换 MIG 后 device plugin 的 migStrategy 要匹配；否则资源名对不上， Pod 会 Pending 或拿到错误 profile。
  • RuntimeClass：hook 模式必须有 nvidia runtime；CDI 模式 runtime 必须启用 CDI。
  • 容器镜像：不要覆盖 NVIDIA_VISIBLE_DEVICES=all；不要把 NVIDIA_DRIVER_CAPABILITIES 裁到只剩 utility。

6.1 GPU 显存 OOM

kubectl logs <pod> --tail=200 | grep -i -E 'out of memory|oom'
kubectl exec <pod> -- nvidia-smi --query-gpu=memory.total,memory.used,memory.free --format=csv

常见误区：

  • 以为 K8s 的 memory limit 能限制 GPU 显存——不能；
  • 以为 time-slicing 的 replica 有独立显存——没有；
  • 以为 gpu_memory_utilization 是硬限制——它是应用自己的预算，不是内核/cgroup 强制；
  • 以为 MIG 一定不会 OOM——MIG 只保证实例的显存容量，模型超过该容量照样 OOM。

6.2 容器 OOM

kubectl describe pod <pod> | grep -A5 'Last State'
kubectl get pod <pod> -o jsonpath='{.status.containerStatuses[*].lastState.terminated}'
cat /sys/fs/cgroup/<path>/memory.events
cat /sys/fs/cgroup/<path>/memory.max

OOMKilled + exit 137 是容器 cgroup OOM 的强信号；但要和「进程自己 exit(137)」区分， 后者不一定是 OOM。

6.3 节点 OOM

dmesg -T | grep -i -E 'out of memory|oom-kill|killed process'
kubectl describe node <node> | grep -A10 'Conditions'

节点 OOM 的重点不是「哪个容器被杀」，而是「为什么 kubelet 没提前驱逐」：

  • memory.available 阈值是否太低；
  • kubeReserved/systemReserved 是否不足；
  • 是否有短时间暴涨，kubelet 10s 轮询来不及；
  • 是否开了 kernelMemcgNotification。

7.1 device plugin health 的实现细节

NVIDIA device plugin 注册 NVML 事件：

EventTypeXidCriticalError | EventTypeDoubleBitEccError | EventTypeSingleBitEccError

收到 Xid critical 后，把设备标为 unhealthy；但默认忽略 13/31/43/45/68/109。 源码见 health.go。

注意：

  • 健康事件是单向的；恢复要重启插件；
  • unhealthy 只降 allocatable，不驱逐已分配 Pod；
  • MIG 设备会按 GI/CI 匹配事件，避免把父卡事件误判到所有实例。

7.2 DCGM health watch

DCGM 的健康 watch 覆盖：

PCIE, NVLINK, PMU, MCU, MEM, SM, INFOROM, THERMAL, POWER, DRIVER,
NVSWITCH_NONFATAL, NVSWITCH_FATAL, CONNECTX, IMEX

见 dcgm_structs.h。

dcgmi health -c          # 检查当前健康
dcgmi health -g 0 -c     # 指定 group
dcgmi diag -r 1          # 短诊断
dcgmi diag -r 2          # 中等诊断（需要独占）
dcgmi dmon -e 230,310,311,393,394,395,396

DCGM 内部默认只把 Xid 119 当作 fatal Xid（可通过 __DCGM_FATAL_XIDS__ 环境变量扩展）。 这说明 DCGM 自己也不把「所有 Xid」等同 fatal。见 DcgmCacheManager.cpp。

7.3 DCGM exporter 的默认 counters

dcgm-exporter 默认 counters 里：

  • DCGM_FI_DEV_XID_ERROR、row remap 393–395、NVLink throughput、PCIe throughput 以及部分 profiling 指标是默认导出的；
  • ECC（310–313）、page retirement、NVLink 错误计数、row remap pending（396）、health status 默认是注释或缺失的；
  • 需要自定义 dcgm-metrics.csv / ConfigMap 才能导出这些字段。

见 default-counters.csv。

这意味着：只看默认 dashboard，你可能根本看不到 ECC/row remap。不要因为「监控没报错」 就认为卡健康；要确认关键字段是否被导出。

7.4 GPU Operator validator / node status exporter

GPU Operator 的组件（driver、toolkit、device plugin、DCGM、DCGM exporter、GFD、NFD、MIG manager、 validator、node status exporter）通过 nvidia.com/gpu.deploy.* 标签编排。validator 负责验证 driver/toolkit/plugin/CUDA 是否就绪；node status exporter 暴露节点状态。

注意：

  • validator 是部署验证，不是持续硬件健康；
  • node status exporter 使用的 nvidia-validator 也不是完整 DCGM 诊断；
  • GPU Operator 的组件版本要与 driver/CUDA 匹配，升级顺序错误会导致整节点不可用。

九、处置 runbook：停止新分配 → 隔离 → 重试 → 升级

9.1 停止新分配

手段命令/对象影响
cordonkubectl cordon <node>阻止新 Pod 调度；不驱逐已有
自定义 taintkubectl taint node <node> nvidia.com/gpu.maintenance=true:NoSchedule需要 Pod 容忍；适合计划维护
DRA DeviceTaintRuleDeviceTaintRule + NoSchedule/NoExecute精确到设备/池；NoExecute 会驱逐
Kueue stopPolicyHold / HoldAndDrain停止新 admission；drain 会驱逐已准入
缩容/删除kubectl scale / delete pod直接减少负载
关队列Kueue ClusterQueue 停用/配额置 0影响整个队列

cordon 只影响调度，不影响已经在跑的 Pod；如果卡已经故障，必须配合 drain/delete 才能把 工作负载移走。device plugin 的 unhealthy 不会替你驱逐。

9.2 隔离

# 节点级
kubectl cordon <node>
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data --force

# DRA 设备级
kubectl apply -f - <<'EOF'
apiVersion: resource.k8s.io/v1
kind: DeviceTaintRule
metadata:
  name: isolate-gpu
spec:
  deviceSelector:
    driver: gpu.nvidia.com
    pool: <node-name>
    device: gpu-3
  taint:
    key: gpu.nvidia.com/unhealthy
    value: "true"
    effect: NoExecute
EOF

注意：

  • NoExecute 会删除使用该设备的 Pod；对训练作业要确认 checkpoint 已保存；
  • 不要在有运行中进程时 nvidia-smi -r 或切换 MIG 模式；
  • NVSwitch/整机故障时，隔离单卡可能不够，要停整个 NVLink 域/fabric；
  • 如果是 IB/RoCE 问题，先隔离网络端口/交换机，不要只重启 GPU。

9.3 重试

场景动作注意
Xid 94（contained）重启应用/容器；方便时 reset其他应用可能不受影响
Xid 95/140（uncontained）先 reset GPU，再重启应用不 reset 直接重试可能再次失败
Xid 48（DBE）reset GPU 或节点重启查 ECC/row remap
Xid 74（NVLink）reset 两端 GPU；查 peer/switch可能是远端 GPU 故障
Xid 79（掉总线）冷重启/reseat；不要热 reset 循环抓 PCIe/BMC 日志
Xid 119/120（GSP）reset/断电重启反复出现按调试指南
驱动不匹配统一驱动/重启节点不要只重启插件
Pod OOM调 limit/request、batch、KV cache区分容器/GPU/节点 OOM

训练作业的重试要和 checkpoint 结合：

  • 先确认 checkpoint 已落盘/可加载；
  • 再删 Pod/重启 Job；
  • 避免调度回同一张故障卡（taint/cordon/device taint）；
  • 记录失败 rank、GPU UUID、Xid、时间，供后续归因。

9.4 升级

升级到厂商/RMA 的信号：

  • 同一 GPU 反复 Xid 79/95/140；
  • ROW_REMAP_FAILED=1 且现场诊断确认；
  • ECC DBE 持续增长，reset 后仍复现；
  • NVLink 错误反复出现，reset 两端/更换 switch 端口后仍复现；
  • PCIe AER 持续报错，reseat/换槽位后仍复现；
  • 多张卡/多节点同时出现，怀疑主板/电源/背板。

升级前准备：

  • GPU UUID、BDF、serial、driver/firmware 版本；
  • nvidia-smi -q、dcgmi diag、dmesg、BMC SEL；
  • 复现步骤/频率/影响范围；
  • 是否已尝试 reset/reboot/reseat；
  • 同节点其他卡是否正常。

十、证据保留清单

故障现场最容易丢的是证据。至少保存：

  • nvidia-smi -q（完整输出，含 ECC、PCI、NVLink、MIG）；
  • nvidia-smi -L、nvidia-smi topo -m；
  • dmesg -T（NVRM、Xid、PCIe AER、OOM）；
  • lspci -vv（BDF、LnkCap/LnkSta、AER）；
  • dcgmi diag -r 2（如果条件允许）；
  • DCGM/exporter 指标（Xid、ECC、row remap、温度、功耗、NVLink）；
  • Pod YAML、container status、allocatedResourcesStatus；
  • device plugin checkpoint / ResourceClaim allocation；
  • 训练 rank 日志、checkpoint 时间点；
  • 变更记录（驱动升级、MIG 切换、节点维护）。

十一、检查清单

  • 故障域是单进程、单卡、单节点还是 fabric？
  • 是 reported / allocated / prepared / usable 哪一层？
  • nvidia-smi 是否能看到卡？容器里看到的是不是分配的那张？
  • 是否区分了 Xid 的应用错误/contained/uncontained/ECC/fabric？
  • 是否查了 ECC 的 volatile 与 aggregate、row remap pending/failed？
  • 是否确认驱动/内核模块/toolkit/CDI/CUDA 版本一致？
  • 是 GPU 显存 OOM、容器 OOM 还是节点 OOM？
  • 停止新分配后，是否真的隔离了已分配 Pod？
  • 重试前是否 reset 了需要 reset 的 GPU？是否保存了 checkpoint？
  • 是否保留了足够的证据再升级/RMA？
