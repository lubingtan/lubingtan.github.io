CPU / GPU 异构资源管理与设备运维：专题总览

结论先行：异构资源管理真正的难点不是「把 GPU 数量写进 Node 的 capacity」，而是保证 资源被看见 → 被正确分配 → 在容器里真的可见 → 硬件真的可用且健康 这四段状态一致。 绝大多数线上事故发生在后两段：调度器认为卡已经分配，容器也 Running，但进程看不到设备、 看到的是错误的 MIG 实例，或者卡已经掉总线而 kubelet 仍把旧 Pod 留在上面。

另一个贯穿全专题的结论是：「分配份额」不等于「隔离保证」。time-slicing 的 replica、 MPS 的线程百分比、HAMi 的显存/算力配额，都是调度或限流语义；只有 MIG 这类硬件分区才同时 提供容量、带宽和故障域隔离。把份额当隔离，是训推混部里尾延迟和 OOM 反复出现的根因之一。

一、四段状态：reported → allocated → usable

把「GPU 可用」拆成四段，是本专题后面所有排障和设计的共同语言。不同实现（device plugin / DRA） 写状态的地方不同，但状态本身没有变。

状态谁写入典型载体怎么观测这一层失败的表现
1. reported（已上报）device plugin 的 ListAndWatch；DRA driver 的 ResourceSliceNode status.capacity/allocatable；ResourceSlice 对象kubectl describe node；kubectl get resourceslicesNode 上卡数正确但资源名为 0；ResourceSlice 缺失/过期
2. allocated（已分配）kube-scheduler + kubelet device manager；DRA 的 ResourceClaim.status.allocationdevice plugin checkpoint；ResourceClaim/var/lib/kubelet/device-plugins/kubelet_internal_checkpoint；kubectl get resourceclaim -o yamlPod Pending；claim 未分配；分配到的设备与预期不符
3. prepared（已准备/可见）kubelet 调 Allocate / NodePrepareResources；runtime 应用 CDIOCI spec、NVIDIA_VISIBLE_DEVICES、CDI device、device nodes、mountscrictl inspect；kubectl exec -- nvidia-smi -L容器 Running 但 nvidia-smi 失败；/dev/nvidia* 缺失；CUDA_ERROR_NO_DEVICE
4. usable（真可用/健康）驱动/NVML、DCGM、device plugin/DRA 健康上报NVML 初始化成功；CUDA context 可建；allocatedResourcesStatus/设备状态nvidia-smi -q；dcgmi health；Pod allocatedResourcesStatus卡可见但初始化失败、ECC/Xid 异常、MIG cap 缺失、性能塌陷

关键点：

  1. reported 只代表「驱动/插件声称有」。device plugin 的 ListAndWatch 可以上报 8 张卡， 但节点可能因为驱动没加载、/dev/nvidia* 权限不对、MIG 配置不一致而一张都用不了。
  2. allocated 只代表「调度账本上记了」。device plugin 的分配记录在 kubelet checkpoint 里； 它不等于容器里已经挂上了设备。DRA 的 status.allocation 同样只是调度结果。
  3. prepared 只代表「运行时做了注入动作」。CDI 注入了 device node，但 device cgroup 仍可能拒绝； NVIDIA_VISIBLE_DEVICES 设了，但 runtime 不是 NVIDIA runtime，容器里照样没有设备。
  4. usable 才是应用视角的真相。CUDA context 能否创建、MIG 实例是否匹配、ECC 是否把页面退休、 Xid 是否把 GPU 打进不可恢复状态，都要单独验证。

device plugin 文档明确写了两件容易反直觉的事：设备被标记 unhealthy 后，kubelet 只降低 allocatable，capacity 不变；已经分配到该设备的 Pod 不会被迁移，会继续留在故障设备上。 见 Device Plugins: Device plugin and unhealthy devices 与 kubelet 源码 manager.go。

二、三个平面，别混在一起排障

平面组件典型问题先看什么
控制面kube-scheduler、ResourceClaim controller、Kueue、Node 对象Pending、配额不足、DRA claim 没分配、抢占没发生scheduler events、Pod conditions、ClusterQueue/Workload status
节点面kubelet、CRI runtime、device plugin、CDI、cgroup设备不可见、Allocate 失败、OOMKilled、CPU throttlekubelet 日志、crictl inspect、cgroup 文件、checkpoint
硬件/驱动面NVIDIA driver、GPU、NVLink/NVSwitch、PCIe、NIC、DCGMXid、ECC、掉卡、NVLink 降级、RDMA 不通nvidia-smi、dcgmi、dmesg、DCGM exporter

同一个症状可能跨三个平面。例如「训练 hang」：控制面看到 Pod 全 Running，节点面看到 NCCL 进程都在，硬件面才发现某张卡 Xid 74 导致 NVLink 链路降级。排障顺序应该是 先确认应用是否真的拿到设备（节点面），再确认设备是否健康（硬件面），最后才怀疑调度（控制面）， 而不是一上来就重新调调度器。

四、十个高频误区

#误区更准确的说法详见
1Node 显示 8 张 GPU，就能跑 8 个 GPU Pod还要看 allocatable、插件健康、MIG 策略、device plugin 是否注册接入链路
2Pod 是 Running，GPU 就一定可用Running 只说明容器进程起来了；设备注入、NVML、CUDA context 都可能失败接入链路
3time-slicing replicas: 4 就是把一张卡切成 4 份只是把 4 个调度槽位映射到同一张物理卡；没有内存/故障隔离共享与隔离
4MIG 可以随便用于分布式训练MIG 实例之间不支持 GPU-GPU P2P（PCIe/NVLink），NCCL 拓扑会退化共享与隔离
5开了 Topology Manager 就会按 NVLink 放置device plugin 只提供 NUMA node ID；Topology Manager 不感知 NVLink/PCIe 距离共享与拓扑
6出现 Xid 就是显卡坏了Xid 13/31/43/45 等常是应用错误；63/64 是行重映射过程；只有部分 Xid 指向硬件GPU 运维
7CUDA out of memory 就是容器 OOMKilledGPU 显存 OOM 是 CUDA/NVML 层错误，不会让 kernel OOM killer 杀容器GPU 运维
8device plugin 标记 unhealthy 会把故障卡上的 Pod 赶走不会；只降低 allocatable，已分配 Pod 继续留在故障设备上GPU 运维
9DRA 可以像普通资源一样被高优先级 Pod 抢占调度器目前不支持对 DRA 资源做抢占；要靠 Kueue 等上层回收训推混部
10MPS 是硬多租户隔离MPS 限制 SM 百分比/内存上限，但错误不隔离，一个客户端致命错误会影响同服务器客户端共享与隔离

六、与站内其它专题的关系

  • HAMi / HAMi-core：HAMi 是「用软件把整卡虚拟成显存+算力配额」的代表实现。本专题的 共享、隔离与拓扑 只把它作为「软共享」一类来比较， CUDA 劫持的实现细节见 HAMi 与 HAMi-core。
  • GPU 算力/显存池化：那篇讲的是「应用视角单卡」的透明性光谱（UVM、MNNVL、API remoting、 显存池化等），本专题讲的是「编排与设备生命周期」；两者在 NVLink/fabric 处交汇，见 GPU 算力/显存池化。
  • 云原生分布式训练：本专题的 训推混部 依赖那边的 membership、故障自愈和 checkpoint 语义；训练故障分层见 训练失败与自愈 与 Checkpoint 与抢占恢复。
  • 容器运行时：OCI、CRI、containerd、shim 与 RuntimeClass 的完整链路见 容器运行时全链路。

七、一页纸检查清单

排障前先问自己：

  • 这是 reported / allocated / prepared / usable 哪一层的问题？
  • 看的是 Node capacity 还是 allocatable？两者差在哪里（reserved、eviction、unhealthy）？
  • Pod 的 QoS 是什么？CPU 是共享还是 exclusive？内存有没有 limit？
  • GPU 是整卡、MIG、MPS 还是 time-slicing？对应资源的隔离语义是什么？
  • 容器里 nvidia-smi -L 看到的是不是调度器分配的那张卡（UUID/BDF/MIG）？
  • 故障是单卡、单节点、单 Pod、单 rank，还是整个 NVLink/IB fabric？
  • 现在的动作是「停止新分配」「隔离」「重试」还是「升级」？有没有可能把故障域扩大？
  • 证据是否保留：dmesg、nvidia-smi -q、DCGM 指标、checkpoint、ResourceClaim、Pod status？
